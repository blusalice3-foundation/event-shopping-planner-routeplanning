目的は、保存障害による白画面、閉じられない画面、限数入力の消失、参加日が空の品目の登録、異なる日付のセル情報が混ざる登録を、小さな変更で防ぐことである。通常の購入・数量・メモ操作、確認と再試行、日付差分保存、描画の最適化は既存の経路を維持する。

## 3. U01: 設定保存の例外を画面へ波及させない

### 3.1 現状と変更境界

設定の`savePreference`は同期処理で、localStorageの例外を伝播する。これを保存先adapterで一律に握り潰すと、[useMapWorkspaceState.ts](../src/app/state/useMapWorkspaceState.ts)が既に持つスマート挿入設定の失敗通知などを壊す。

したがってadapterと`PreferencePersistencePort`のシグネチャは維持し、保存例外を捕捉していない次の5hookだけを保護する。

- [useUIVisibilitySettings.ts](../src/hooks/useUIVisibilitySettings.ts)
- [useThemeMode.ts](../src/hooks/useThemeMode.ts)
- [useNumberCellOutlineStyle.ts](../src/hooks/useNumberCellOutlineStyle.ts)
- [useDisablePriceUndefinedCheck.ts](../src/hooks/useDisablePriceUndefinedCheck.ts)
- [useDisableLimitedPurchaseQuantityCheck.ts](../src/hooks/useDisableLimitedPurchaseQuantityCheck.ts)

### 3.2 実装手順

1. 各hookの既存effect内で、`savePreference`の呼出しだけを局所的なtry/catchで保護する。既に保護済みの他hookと同じく、保存失敗時も現在のメモリ上の選択値を維持する。
2. Themeではテーマの適用、system設定時のmatchMedia監視とcleanupを保存例外のcatch範囲の外に置く。保存に失敗しても画面のテーマ変更は機能させる。
3. 表示設定パネルの「閉じると適用」、数量チェックのオン・オフ、セル枠の許容値と初期値は維持する。
4. 自動再試行timer、失敗用の全体state、毎renderの保存、エラー値を含むログは追加しない。既存effectの依存値が変わったときの保存試行にとどめる。
5. 設定保存の失敗を理由に品目の「保存済み」判定を変更しない。端末設定の永続化失敗をデータ保存成功として偽装するAPI変更も行わない。

### 3.3 受入条件

- 初回effectと設定変更後のeffectが例外を受けても、アプリと変更したメモリ値が残る。
- 保存可能な通常条件では、設定が従来どおり再読込後に復元される。
- Themeのsystem監視・解除、表示設定の適用、既存のスマート挿入失敗通知が維持される。
- 移行済みIndexedDBが正常でlocalStorageの読取が可能な「書込容量不足」では、一覧表示、通常の品目保存、JSONバックアップ保存を完走できる。
- localStorageのgetter・読取自体が利用不可の場合は、画面の白画面化防止と、既存の復旧・バックアップ失敗案内が表示できることを確認する。現行backupWorkerも読取を行うため、全種類のstorage障害でバックアップ成功を保証した扱いにはしない。
- 移行前アーカイブ等が失敗して既存の復旧画面に入るケースは、この設定保存例外とは区別して記録する。

## 4. U02: 閉じる操作から要求IDへクリックイベントを渡さない

### 4.1 最小変更

[AppOverlayLayer.tsx](../src/features/app-shell/components/AppOverlayLayer.tsx)で、EventRenameDialogの`onCancel`とExportOptionsDialogの`onClose`を、引数なしのラッパにする。

```tsx
onCancel={() => eventOverlayCommands.close()}
onClose={() => eventOverlayCommands.close()}
```

`close`をクリックハンドラーへ直接渡さない。コントローラ側は、既にレンダー時の要求ID・kindを捕捉している。要求IDを新たに各画面へ伝播したり、コントローラの引数判定・旧要求拒否を緩めたりする必要はない。

### 4.2 受入条件

- 名称変更のキャンセル、同名入力による既存の閉鎖経路、出力設定のキャンセルと×が機能する。
- キャンセルではデータ保存・ダウンロード・名称変更を開始しない。
- 閉じた後に再度開ける。古い画面から保持したコールバックで後続の別要求を閉じない。
- 正常な名称変更とExcel出力、出力処理側の`onClose()`は従来どおり機能する。
- 実controller・実Overlay・実ダイアログを接続したクリック試験を置く。閉じる関数を`vi.fn`へ置換しただけの試験で完了扱いにしない。

## 5. U03・U04: 限数ダイアログ内でタッチ・キー操作を完結させる

### 5.1 維持する既存処理

[LimitedPurchaseDialog.tsx](../src/components/LimitedPurchaseDialog.tsx)はPortalで表示されるが、Reactのタッチイベントは親の[FocusMode.tsx](../src/components/FocusMode.tsx)へ伝播する。単品のダイアログはカード内で管理されるため、集中モードへ全カードの開閉stateを集約する方式は採用しない。

数量のparse、予定数量と実購入数の検証、同数・超過確認の判定、予定数量の変更意図、対象ガード、結果のonSubmit、保存待ち・失敗保持の契約は維持する。U04は確認の表示・失効に伴うフォーカス移譲だけを補い、数量の受理条件を変えない。

### 5.2 U03の実装手順

1. 主入力のLimitedPurchaseDialogと、兄弟として表示される[LimitedPurchaseConfirmDialog.tsx](../src/components/LimitedPurchaseConfirmDialog.tsx)のrootに、touchstart・touchmove・touchend・touchcancelの伝播遮断を追加する。既存のイベント停止関数を再利用し、新しいイベント基盤を作らない。
2. [SingleQuantityLimitedPurchaseChoiceDialog.tsx](../src/components/SingleQuantityLimitedPurchaseChoiceDialog.tsx)のrootも同じ境界として扱う。既存のクリック・pointer停止や選択肢、初期フォーカスは維持する。
3. `preventDefault`や`touch-action: none`は追加しない。入力欄の選択、ソフトキーボード、縦スクロールを妨げない。
4. 新しいdocument touch listener、カード全体の監視、移動の保存完了待ちは加えない。
5. ジェスチャー開始・終了の境界に残存状態がないか試験する。ダイアログ内の通常スワイプが止まることを主対策とし、失敗が残る場合に限りFocusModeの対象判定と既存touch refのリセットを局所的に補強する。通常のカード上のスワイプ判定は変更しない。

### 5.3 U04の実装手順

1. 主入力ダイアログに既存`useModalDialogBehavior`を適用し、rootへ`dialogRef`と`onDialogKeyDown`を接続する。初期フォーカスは実購入数の入力欄とする。共通hookの全呼出元を改修せず、限数入力とカードの接続内で補う。
2. hookの`isOpen`は主ダイアログの開閉だけに連動させる。同数・超過確認や次品目への移行でfalse/trueへ切り替えず、主ダイアログをkeyで再マウントしない。起点の捕捉・スクロールロック・最終閉鎖時の復帰を維持し、確認側の初期フォーカスをcleanupで奪わない。
3. `FocusMode`の全限数入力は、同じ更新内で次品目へ進み、`isOpen=true`のまま主ダイアログを再利用する。既存の対象識別値`itemId`・`dialogKey`の変更に合わせ、主入力内の局所的な処理で次品目の実購入数へフォーカスを移す。前品目の確認が破棄され、新しい入力DOMが確定した後に実行する。新しい確認が表示中なら主入力へ奪い返さない。
4. 同一画面の保存反映等で`initialPlanned`が変わり、同数・超過確認が失効した場合も、確認の閉鎖後に主入力内へ明示的に戻す。この自動失効では実購入数欄へ戻し、既存の実購入数・予定数量の編集意図を維持する。通常の「入力に戻る」「修正する」・Escapeでは、従来どおり保存ボタンへ戻す。通常の1文字入力や無関係なrenderではフォーカスを初期化しない。
5. 主ダイアログの`aria-modal`切替、確認側の既存Tab循環と初期フォーカスを維持する。確認取消等の既存の遅延復帰処理は、次品目・新しい確認・主入力閉鎖後に古い対象へ作用しないよう、取消または対象識別値の照合を局所的に補う。
6. 主rootで処理したEscapeは伝播を止め、既存document Escape listenerへ二重に渡さない。確認側のEscapeは確認だけを閉じる既存の分岐へ渡す。1回のEscapeでonCancelを2回呼ばない。
7. [ShoppingItemCard.tsx](../src/components/ShoppingItemCard.tsx)のラジアルメニューから限数入力へ進む場合は、既存`closePurchaseStatusMenu({ restoreFocus: false })`で閉じ、背景の購入状態ボタンへ戻す`requestAnimationFrame`・timeout予約を発行しない。数量1の選択ダイアログを経由する場合もフォーカスを次のダイアログへ引き継ぐ。通常の状態選択・同状態での取消の復帰は維持する。
8. ラジアル内の選択肢は遷移時にunmountされるため、予約抑止だけで復帰先を確保した扱いにしない。安定した`purchaseStatusButtonRef`を起点として保持し、カード内の既存閉鎖処理等を局所的に補って、限数入力の取消・最終閉鎖時に戻す。必要な任意のref・propは対象部品間に限定する。共通hookの`fallbackFocusRef`はコンテナ内を探索するAPIなので、ボタンrefをそのまま渡して復帰できると仮定しない。
9. 閉じた後は起点へフォーカスを戻し、起点が削除・非表示になった場合に無関係な背景ボタンへ移さない。遅延した復帰処理が、再表示したダイアログから背景へ奪わないことも確認する。
10. 新しいモーダルライブラリや全画面のinert処理、document全体のフォーカス監視は導入しない。Portalや兄弟確認まで無効化する副作用を避け、対象rootと遷移時の局所処理で完結させる。

### 5.5 必須の回帰ケース

単品・全限数、予定数量1・2以上・既存20超、同数確認・超過確認、PC・スマートフォンを組み合わせる。主入力と確認それぞれで左右スワイプ、Tab、Shift+Tab、Enter、Escapeを確認する。

入力中に移動・保存が発生しないことだけでなく、閉じた後に通常移動が復帰すること、同じイベントで再度開けることを確認する。共通確認部品の呼出元であるItemEditDialogとLimitedPurchaseMissingListViewも回帰対象とする。

追加レビューの再現は、次の実接続で固定する。

- 実`FocusMode`と実ダイアログで、全限数の2品目以上を連続入力する。同数確認・超過確認の確定、通常保存、「後で入力」の各経路で、次品目の実購入数へ移り、直後のTab・Shift+Tab・Enterが背景の購入・訪問移動を実行しないことを確認する。`isOpen`を試験側で閉じ直して再現条件を消さない。
- 同数・超過確認中に、同一画面の保存反映によって予定数量を更新する。確認失効後に`document.activeElement`が主入力内にあり、BODYへ落ちず、未送信入力と変更意図が残り、失効した確認から保存されないことを確認する。

## 7. U06: セルポップアップの操作元を固定し、日付切替で失効させる

### 7.1 操作スコープ

Appで既に訪問リストへ渡している`application.coordinator.generation(eventName)`を再利用する。新しい世代管理や保存データは作らない。

操作スコープは、次の4つのプリミティブ値を配列化してJSON.stringifyした識別子とする。

1. 実際のイベント名。
2. 既存coordinatorのUI側イベント世代。
3. `normalizeExecutionVisitDay`で比較する対象日。
4. 実際に解決されたマップキー（`currentMapTabName`）。

この世代は品目ガードのdurableGenerationと区別する。通常の購入・数量保存ではUI世代を増やさず、イベント置換・復元など既存の失効条件を使う。イベント名やマップ名の区切り文字による衝突を避けるため、文字列の単純連結は使わない。

### 7.2 実装手順

1. [App.tsx](../src/App.tsx)→[AppMainContent.tsx](../src/features/app-shell/components/AppMainContent.tsx)→[MapView.tsx](../src/components/map/MapView.tsx)へ、現在の操作スコープを渡す最小のpropを追加する。型と実呼出元・テストfixtureを同時に更新する。スコープを欠いた場合に安全でない既定値へ落とす設計にはしない。
2. セルを開くたびに、MapView内の一時連番から新しいpopup session IDを発行する。popupStateへ操作スコープ・session ID・日付原文を保存し、現在の未受付操作の所有者も安定したrefで保持する。block・number・位置・品目と同じ操作元に属する値として管理する。新しい永続世代やDBレコードは作らない。
3. render時に保存したスコープと現在値、session IDと現在の所有者を比較する。不一致ならそのrenderからポップアップを表示せず、子の[CellItemsPopup.tsx](../src/components/map/CellItemsPopup.tsx)だけをunmountする。effectで閉じるだけの一瞬の操作可能期間を作らない。
4. スコープ切替時は古いpopupStateも閉じた状態へ破棄し、未受付sessionを失効させる。A→B→Aや、同じscopeで別のpopupを開く場合に旧状態・旧callbackが復活しないことを保証する。子限定のkey・条件mountにはsessionも反映し、MapViewやCanvas全体を再マウントしない。
5. 子へ渡すeventDateは、開いた時に保存した日付とする。現在の日付だけを旧セルのblock・numberへ合成しない。
6. ポップアップ由来の変更コールバックは、受付直前に、開いた時のscope一致、現在も有効なsession ID一致、期待する所有者種別の一致を全て検査する。日付がA→B→Aと戻っただけで旧callbackを再受理しない。現在scopeは最新のcommitを参照する安定したref等で保持する。Reactの未確定renderの値を正本にしない。
7. 対象は新規追加、品目編集・状態変更・削除・優先度変更、詳細編集の表示要求、実行列への追加・解除、一括操作、挿入位置選択を経由する変更とする。既存の位置計算・挿入順・確認内容は維持し、受付前の文脈チェックと後述の中継表示・入力の有効性判定を接続する。利用者の閉鎖、scope切替、MapViewのunmount時は未受付sessionを失効させる。正当な詳細編集の起動と中継への所有権移動では、後述の引継ぎ順序に従う。
8. refで現在スコープを更新する処理は、同コンポーネントのlayout effect内でcommitと同期する。比較は固定個数の識別値・IDの比較とし、全品目・全セルのハッシュ計算、mapDataの参照一致による失効は行わない。sessionの開閉・所有権移動は同じ操作内でrefも同期し、二重の正本を作らない。
9. 子unmountの導入に合わせ、既存の長押しtimerを閉鎖・unmount時に解除する。旧timerでメニューや入力状態が復活しないようにする。子のcleanupが、既に中継へ移った所有権まで失効させないよう、UIのtimer cleanupと操作sessionの失効を分ける。
10. `MapViewProps.onUpdateItem`を実呼出しに合わせて`(item: ShoppingItem, baseline?: ShoppingItem) => void`とし、ガード用ラッパも`(item, baseline)`を受けて両引数をそのまま中継する。関連するprops・型・呼出元も照合し、`CellItemsPopup`が第2引数で渡す編集開始時の品目を途中で捨てない。比較元を最新品目へ置換したり、ガード内で作り直したりしない。
11. `CellItemsPopup`の直接ボタンと長押し編集内の「限数を編集」は、どちらも有効なpopup sessionのガードを通して`onEditRequest(item)`を呼び、詳細編集の表示要求を渡してから`onClose()`する。現在の`onClose()`→`onEditRequest()`の順序を維持しない。閉鎖後の旧要求を許可する例外は作らず、ガード不一致の要求で後続sessionのUIを閉じない。正常に引き継いだ詳細編集は既存overlayの要求管理に任せる。

### 7.3 保存との境界

スコープ照合は操作を受け付ける前の保護である。照合後に受理された品目差分・保存要求は、既存のキューとガードへ渡す。保存待ちに別日へ移動したことだけを理由に、新たな取消・破棄・別日への付け替えをしない。

`AppMainContent`→`App`→`useShoppingItemMutationCommands.updateItem`の既存経路は、編集開始時の`baseline`と編集後の品目との差分だけを最新品目へ合成し、保存コマンドへも比較元を渡す。この契約を型と中継の両方で維持する。同一画面の保存待ち・再試行中に反映された購入状態・数量・メモは、今回明示的に編集したフィールド以外を古い編集値で戻さない。通常のpopup更新ではsessionを消費せず、保存に続く優先度更新や同じpopupの連続操作も受け付ける。

ポップアップから別の挿入位置確認へ処理が引き継がれる場合は、未受付の操作元scope・session IDと所有権を中継stateへ移す。対象は`mapRouteInsertPending`、`insertDialogState`と`batchInsertPendingIds`、Worker待機の`waitingRouteInsert`とする。既存stateへ付随させ、別の並列操作ストアは作らない。最終受付時にscope・session・所有者を同じように照合し、途中でUIだけ閉じたことを保存成功とみなさない。複数品目追加とホール所属反映を含む一つの既存受付の途中でsessionを消費し、後半だけ拒否する構造にしない。既に保存処理へ受理された操作との区別をテストで固定する。

### 7.3.1 未受付操作の所有権

| 状態・遷移                              | sessionの扱い                                         | 受付の条件                                                    |
| --------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------- |
| popupを開く・開き直す                   | 新session IDを発行し、旧sessionを失効                 | 現在scope＋新ID＋所有者popupが一致                            |
| 同じpopup内で連続して状態・金額等を変更 | popup sessionを維持。各受付済み差分は既存キューへ渡す | 毎回同じ受付前ガードを通す。通常の連続操作を止めない          |
| popupから詳細編集を開く                 | 有効なpopupで表示要求を渡してから閉鎖・失効する       | 両編集ボタンともガード→編集起動→閉鎖。以後は既存overlay管理   |
| popupから挿入位置確認・Worker待機へ進む | 所有者を中継へ移してからpopup UIを閉じる              | 旧popup callbackは所有者不一致で拒否。中継だけが確定可能      |
| 中継を確定する                          | 一つの最終操作を受理し、中継sessionを消費             | 現在scope＋ID＋所有者中継が一致。関連する受付を途中分断しない |
| 利用者の取消・scope切替・親unmount      | 未受付sessionを失効                                   | 旧callbackは日付が戻っても拒否                                |
| 受理済み保存が実行中・失敗・再試行      | UI sessionから分離し、既存操作IDで継続                | 既存mutationの対象ガード・確認・CASに従う                     |

中継へ移った後の子unmountと、利用者の取消を同じ処理にしない。中継の保存前にscopeが変わった場合は失効させ、保存受付後のscope変更では受理済み操作を取り消さない。

### 7.3.2 中継の表示・Canvas入力・Worker再開

sessionの失効だけでは、旧日の地図snapshotや位置選択案内が残る。次の表示・入力の境界も、同じ中継の有効性判定へそろえる。

1. render時に現在scope・session ID・中継所有者が一致するpendingだけを有効とする。`mapRouteInsertPending`等の生stateをそのまま表示へ渡さず、不一致のrenderから旧UIを出さない。
2. `mapDataForCanvas`、ルート点・線のoverride、strict miss用snapshot、`forceRouteVisible`、`routeInsertSelectionActive`、位置選択案内・エラー・重複候補、挿入確認ダイアログ、popup由来の待機案内は、有効な中継だけから導出する。失効時は現在の日付・マップの通常表示と通常のセル入力へ戻す。中継由来の旧snapshotをB日の見出しの下に残さない。
3. Canvasの位置選択hit・miss、重複候補の選択、確認・取消の各callbackも、受付直前に同じscope・ID・所有者を検査する。表示を消すだけで旧callbackを有効に残さない。旧取消で新しい中継を閉じない。
4. 日付を含むscope変更時は、未受付の`mapRouteInsertPending`と対応ref、`insertDialogState`・`batchInsertPendingIds`、`waitingRouteInsert`に付随する状態・所有権を破棄する。即時の表示・入力の遮断はrenderで行い、commitに合わせたcleanupでstate/refも整合させる。A→B→Aで旧中継が再表示・再開しないようにする。
5. Worker完了による待機からの再開・直接追加へのfallbackも、実行前に現在scope・session・中継所有者を再確認する。`routeCalculation.key`の一致だけで正当としない。失効済みの応答は未受付操作を再開せず、追加保存・所属更新を発行しない。
6. 変更はMapView側の中継の表示・入力・結果消費に限定する。Worker基盤、ルート計算の署名・再計算条件、Canvas・viewport本体は変更せず、scope変更だけを理由に計算を再送しない。受理済み保存のキュー・操作ID・失敗保持・再試行は、このcleanupから切り離して継続する。

### 7.4 受入条件

- A日のセルから、キーボード・マウス・タッチのどの方法でB日へ移動しても旧ポップアップが閉じる。
- 閉鎖前に保持した旧コールバックから変更要求が発生せず、保存・ダウンロード・別日の品目作成が0回である。A→B→Aの往復後や同scopeの別popup表示後でも旧callbackの受付は0回である。
- 別イベント、同日別マップ、同名イベントの置換・復元による世代変更でも旧状態が残らない。
- A→B→Aで以前の追加・編集・長押しstateが再表示されない。
- 同じ日・同じマップの通常購入・数量・メモ・優先度更新では、スコープが不要に変化せず、入力中のポップアップを閉じない。
- 通常のセル選択、pointerup後の互換click抑止、長押し、品目編集、限数入力、実行列追加・挿入位置選択を維持する。
- 同一画面で編集を開始し、保存待ち・再試行中に別操作の購入状態・数量・メモが反映された後で保存する。第2引数の編集開始品目が実mutationまで届き、未編集の最新値は残り、今回明示編集した値は反映される。同scopeの連続更新・優先度更新も受け付ける。
- 直接ボタンと長押し編集内の「限数を編集」を、実MapViewのsession管理と接続する。どちらも詳細編集が1回開いてからpopupが閉じ、閉鎖後の旧callbackは拒否される。`onEditRequest=vi.fn`だけの試験で完了扱いにしない。
- マップ上の位置選択中、挿入確認ダイアログ中、Worker待機中の各経路でA→BおよびA→B→Aを試験する。旧地図・ルート・案内・重複候補・確認が消え、Canvasが現在日の通常入力へ戻り、旧hit/miss・確定・取消・Worker完了からの追加・保存・所属変更は0回である。
- MapView全体の再マウント、Canvas再生成、操作スコープだけを理由としたルート再計算・追加保存が発生しない。

## 10. 実装・検証の進め方

### 10.1 着手前

1. `git status --short`で作業状態を確認する。第三者・利用者の変更を削除してクリーンにしない。既存変更がある場合は削除せず、別のクリーンな作業ツリー等へ分離して着手する。この計画による変更だけを追跡する。
2. 各変更前に、その単位で何を変えるか1〜3行で宣言する。
3. 対象のencoding候補・BOM・改行を確認してからstrict UTF-8で読む。既存のencoding・BOM・改行を維持する。
4. 参照コミットから実装時点までの差分を確認し、該当する関数・型・呼出元が変わっていれば実コードへ計画を合わせる。
5. 再現テストを固定し、元の不具合による失敗と、環境・fixture・独立課題による失敗を区別する。データ破壊を伴う容量試験は隔離したブラウザcontextで行う。

| 段階 | 作業           | 通過条件                                                                             |
| ---- | -------------- | ------------------------------------------------------------------------------------ |
| A    | 再現と基準採取 | 各対象の失敗が修正前ソースで説明でき、正常系と測定条件を固定できる                   |

## 12. 性能の維持と測定

### 12.1 実装上の上限

| 対象 | 追加処理を行うタイミング          | 許容する範囲                                                                   |
| ---- | --------------------------------- | ------------------------------------------------------------------------------ |
| U01  | 既存の設定effect実行時            | 既存の1保存呼出しをtry/catchで囲む。新しいtimer・全体stateなし                 |
| U02  | 閉じるボタンの操作時              | 引数なしラッパの1呼出し                                                        |
| U03  | ダイアログ内のtouch時             | イベント伝播停止だけ。通常リストの全件判定なし                                 |
| U04  | 開閉・対象変更・確認失効・キー時  | 局所refのfocus移譲と対象root内の候補走査。1文字ごとの全DOM走査・再初期化なし   |
| U05  | 手動保存送信時                    | 入力された日付1文字列の判定。全品目再検証なし                                  |
| U06  | scope変更・表示・受付・中継再開時 | 固定4値とsession ID・所有者の比較、既存一時state/refの破棄。全件走査/cloneなし |
| U07  | イベント選択時                    | 実在・lengthの分岐。追加の全体DB読取なし                                       |

共通hookやcallbackを接続するために、品目配列・mapDataを毎renderで作り直さない。依存値を安定させ、focus処理は開閉・対象変更・確認失効等の必要な遷移だけで実行し、数量入力ごとに再実行しないことを確認する。有効中継からの表示導出は既存snapshotの選択にとどめ、clone・追加のルート計算・保存を発行しない。新しい処理を通常の「次へ・戻る」や保存完了待ちへ重ねない。

### 12.2 通過基準と条件数

AGENTS.mdの基準として、150／500品目、分散・集中配置、地図あり・なし、PC・スマートフォンの全16条件を必須とする。各条件の実行購入・実行記録・集中購入・集中記録・次へ・戻るの6操作について、各20サンプル以上、中央値55.0ms以下、95%点100ms以下を全て満たす。

計画作成時点の`tests/browser/responsive-performance.spec.ts`は、さらに1,500品目を含む全24条件を列挙している。実装時はこの既存テストを省略せず、1,500品目を含む24条件を同じ基準で確認する。AGENTSの16条件は必須の下限であり、現行24条件を16条件へ削減する理由にしない。

保存完了時間は操作反応と別に記録する。過去の50ms基準と当初の合否、生サンプルを改変しない。新基準による再判定、修正前の新規測定、修正後の測定を別々に保存する。

### 12.3 測定の手順

1. 実装前と実装後を同じ端末・ブラウザ版・viewport・データ・ビルド設定で測る。コミット、未コミット差分のハッシュ、生成artifact、実行環境を記録する。
2. 機能・型検査が通った候補をビルドし、性能測定はブラウザworkerを1にして単独実行する。他のテスト、ビルド、CPUプロファイルを同時実行しない。
3. 既存ハーネスのサンプル・中央値・95%点・保存時間・描画回数の添付を保存する。全条件を列挙し、欠測・失敗を他条件の平均で埋めない。
4. ダイアログを使わない通常6操作に加え、限数主入力の開く・数量入力・確認・閉じる、一括入力の次品目移譲、確認失効、ラジアルからの引継ぎと取消、日付切替でのpopup・中継解除を測る。中継解除は位置選択・挿入確認・Worker待機と旧応答到着を対象にする。これらの診断値を通常6操作の合格値に混ぜない。
5. 追加の対象操作の診断は各20回以上と初回値を別途記録する。操作反応が中央値55.0ms・95%点100msを超えた場合は原因を調べ、完了判定前に解決する。Worker待機の開始・解除・旧応答消費の反応と計算完了までの経過時間も分け、保存完了は別集計とする。
6. 通常6操作が基準内でも、修正前後で持続的な悪化、全体再描画、不要な追加保存が見つかれば原因を確認する。閾値の緩和で通過させない。
7. 失敗後の再測定は理由・変更点・全試行を残す。通った回だけを選別せず、修正した候補に対する必要範囲を再測定する。

## 14. 文字コード・差分の検証

新しい文書はUTF-8・BOMなし・LFとする。既存ファイルは個別の元encoding・BOM・改行を維持する。ファイル操作はPowerShellで行い、書込みには明示的なencodingを指定する。ファイル保存のための`>`・`>>`は使わない。

保存後はstrict UTF-8で再読込し、日本語の代表行を確認する。`ユーザー登録`、`エラーが発生しました`等の既存代表文字列、U+FFFD、疑わしい疑問符の増加、BOM、改行構成を確認する。異常を検出した場合は保存・実装を進めず報告する。

`git diff --check`、`git diff --stat`、実差分で、無関係な大量整形・改行だけの差分・生成物混入がないことを確認する。修正後は差分と文字コードの変化の有無を明示する。

### 16.3 切り戻し

各単位は独立コミットにし、不具合が出た単位を差分単位で戻せるようにする。U03・U04はモーダルの操作契約が揃う単位で扱い、片方だけ戻す場合は残る側のtouch・focus・Escapeを再検証する。

DB・バックアップ形式は変更しないため、この計画の切り戻しにデータ移行は要らない。保存済みの購入記録・品目・マップを消して切り戻さない。利用者データに対する`localStorage.clear()`やサイトデータ削除を復旧手順にしない。

公開・配布・リリース承認は実装計画とは別の既存運用に従う。機能・性能・データ保持の根拠がそろった候補をレビュー可能にしてから、必要な最終手続きへ進める。
