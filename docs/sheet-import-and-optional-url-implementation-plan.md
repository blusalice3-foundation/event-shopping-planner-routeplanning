# シート取込の行選別と任意URLの統一：修正・実装計画

- 作成日：2026-10-16（日本時間）
- 対象：event-shopping-planner-routeplanning-1.9.6.7
- 改訂日：2026-10-16（日本時間）。診断情報の画面中継と変更前後の性能比較に加え、一括取込の参照一致、URL補完から除く行の範囲、読込内部を含む起動時の総保存回数を具体化。
- 状態：実装前の計画。今回改訂するのは本書のみであり、アプリのソースコードは変更しない。
- 性能検証対象：150品目・500品目。1,500品目の検証は今回の実行対象・完了条件から除外する。
- 利用前提：PWAの単一画面。同じデータを別タブ・別ウィンドウで同時編集しない通常運用を対象とする。

## 1. 概要

スプレッドシートに必須項目が欠けた行が混在すると新規作成・更新全体が止まる問題と、URL未入力の手動追加で保存が失敗する問題を修正する。

行の選別は既存のCSV解析処理に組み込み、サークル名・参加日・ブロック・番号がすべて入力済みの行だけをアプリで扱う。欠落行があっても、採用した行で新規作成・更新を進める。

URLは任意入力のままとする。未入力の品目データは「url項目なし」に統一し、追加・編集・シート更新・起動時の互換対応・復元・保存再試行で同じ規則を使う。

既存の保護設定、購入記録、数量確認、重複照合、保存キュー、競合検出、巡回情報の参照整理を活用する。通常操作に全品目の再走査・全データ複製を追加せず、確認対象・保存対象・保存後の画面反映を一致させる。

## 2. 合意済みの仕様と対象範囲

### 2.1 必須4項目の判定

| 項目       | 採用条件                             |
| ---------- | ------------------------------------ |
| サークル名 | 前後の空白を除去した結果が空ではない |
| 参加日     | 前後の空白を除去した結果が空ではない |
| ブロック   | 前後の空白を除去した結果が空ではない |
| 番号       | 前後の空白を除去した結果が空ではない |

- 4項目すべてが条件を満たす行だけを採用する。
- 1項目以上欠けた行は除外し、ほかの行の処理を続ける。
- 判定のために数値変換や日付変換を追加しない。文字列の番号「0」は空欄と区別する。
- タイトル・価格・備考・URLを、この変更で新たな必須項目にしない。
- 価格・数量の既存の解釈、数量の不正値に対する既存の扱いを維持する。
- 手動追加に4項目必須の条件を広げない。

### 2.2 既存品目と0件の扱い

| 状況                                         | 動作                                         |
| -------------------------------------------- | -------------------------------------------- |
| 正常行と欠落行が混在                         | 欠落行を除外し、正常行で続行                 |
| 新規作成の最終採用品目が0件                  | イベントを作成せず、取込対象0件と表示        |
| 取込済み品目の必須項目がシートで空欄になった | 更新時に削除候補とする                       |
| 更新時にすべての行が対象外になった           | 削除候補数と保護対象数を表示し、確認後に反映 |
| 更新確認をキャンセル                         | 品目・更新元などを変更しない                 |
| 通信・CSV解析・形式確認が失敗                | 取込失敗とし、0件更新へ変換しない            |

削除候補には既存の保護設定を適用する。full・deletable・none、およびsourceから求める既定値の挙動は現在の実装に従う。削除が確定した品目に対する実行列・訪問リスト・巡回設定などの参照整理も、既存の更新処理を通す。

### 2.3 適用する入力経路

| 経路                                     | 必須4項目による行選別   | URLの未入力統一 |
| ---------------------------------------- | ----------------------- | --------------- |
| スプレッドシートURLからの新規作成        | 適用                    | 適用            |
| イベント一覧からのシート更新・更新元切替 | 適用                    | 適用            |
| 共通CSVパーサーを利用する品目表の取込    | 適用                    | 適用            |
| 一括貼り付け追加                         | 現行の4項目判定を共通化 | 適用            |
| 手動での単品追加・編集                   | 入力条件を拡張しない    | 適用            |
| 一覧・実行・集中モードからの追加         | 入力条件を拡張しない    | 適用            |
| マップのセルのポップアップからの追加     | 入力条件を拡張しない    | 適用            |
| 完全版JSON・XLSXの復元                   | 行選別を追加しない      | 適用            |
| 保存済みデータの起動時読込・保存再試行   | 行選別を追加しない      | 適用            |

完全版の復元や手動品目には、ブロック・番号が空欄の有効な既存データが含まれ得る。そのデータを表取込の条件で削除しない。

### 2.4 今回の範囲外

- 1,500品目を主対象とする性能検証・追加の規模別検証。
- 別タブの同時編集だけを再現条件とする指摘を、今回の修正必須条件に追加すること。
- URLの必須化や、すべての入力経路への新たなURL形式制約の追加。
- 購入状態、限数数量、保護設定、日付・スペースの照合方法の再設計。
- DB・バックアップ・worker通信のバージョン変更を、この表現統一だけを理由に行うこと。
- 過去の計測値・当初の合否・既存の1,500品目の測定記録を改変すること。

既存の他タブ関連テスト・1,500品目のテスト定義は削除しない。今回の検証対象は実行時に選択する。

## 3. 原因と修正の接点

| 問題                             | 現在の原因                                                                    | 主な接点                                                                                                                                                            |

## 4. シート解析・行選別の実装設計

### 4.1 処理順序

1. CSV以外の応答とCSV構文エラーを検出する。
2. 既存の列形式・見出し・メタデータの確認を行う。
3. 現行の空行・集計行・明確な案内行の処理を維持する。
4. 入力経路ごとの列位置から必須4項目を取り出す。
5. 共通の採用判定を行い、不足があれば診断情報を記録して次へ進む。
6. 必須4項目を通過した行の価格・数量の生値・備考・URL等を、既存規則で読み取る。この時点で数量不正を理由にURL補完対象から外さない。
7. 必須4項目を通過した行に、既存のnormalizeSheetItemsUrlsによるURL補完を行う。サークル・参加日のグループ、入力順とURL選択規則を維持する。
8. 新規取込では、その後に既存の数量判定を行い、不正数量行を警告して新規追加から除く。更新では既存品目の数量保持・購入済み数量確認など、従来の数量同期方針を維持する。
9. 完成した品目を正規化し、追加または更新差分へ渡す。一括取込の入力とsourceRowsの対応は6.5の契約を維持する。

「除外行のURLを引き継がない」は、今回新たに通常除外する必須4項目欠落行に限定する。数量不正行まで補完対象から除く仕様変更は含めない。現行の新規取込はURL補完後に数量不正行を除いているため、必須4項目がそろう数量不正行にだけURLがある場合、その行を追加しなくても、同じサークル・参加日の正常行への補完結果は残す。

配置情報は、必須項目欠落行・数量不正で追加しない行のどちらからも採用品目へ転用しない。通常除外と数量警告の件数は別に保持する。再解析や追加通信を増やさず、既存の解析・変換の流れで処理する。

### 4.2 共通判定と診断情報

共通判定は抽出済みの4項目を受け取り、不足項目の一覧を返す小さな関数とする。Google形式のM列開始と旧CSV形式のA列開始など、列位置の違いは各パーサーで解決する。

readEventCsvの既存ループに診断情報の集計を組み込む。全文を解析し直す処理や、同じシートへの追加リクエストは行わない。

提案する診断型の例：

```typescript
type RequiredSheetField = "circle" | "eventDate" | "block" | "number";

interface SheetRowExclusionSummary {
  excludedCount: number;
  missingFieldCounts: Record<RequiredSheetField, number>;
  examples: Array<{
    sourceRowId: string;
    lineNumber: number;
    missingFields: RequiredSheetField[];
  }>;
}
```

- examplesは先頭20行を上限とし、全件数は別に保持する。
- 同じ行で複数項目が欠けた場合、除外行数は1、項目別不足件数はそれぞれ加算する。
- sourceRowIdと物理行番号を保持する。除外後の配列番号で置き換えない。
- 品目オブジェクトや永続データに診断情報を埋め込まない。
- 数量不正による除外・更新見送りは、必須4項目欠落による除外と別に集計する。

### 4.3 通常除外と既存警告の分離

必須4項目欠落の除外は、取込結果に付随する情報として扱う。既存のwarningsやCsvReviewRequiredを、この通常除外だけで発生させない。

未知のメタデータ、対応関係の未解決、配置の不整合など、既存仕様で確認が必要な警告は維持する。既存の警告確認を一括で解除しない。

parseEventItemsFromCsv等、既存の配列戻り値を使う呼出し元の契約は可能な限り維持する。新規作成・更新画面には診断情報付きの結果を渡せる経路を設け、内部では同じ解析結果を利用する。

## 5. 新規作成・更新画面の実装設計

### 5.1 新規作成

- 実際に保存する品目数と、必須4項目欠落による除外件数を区別して表示する。
- 最終採用品目が0件ならonBulkAdd等の保存処理を呼ばない。
- 0件・失敗・キャンセル時は入力欄を維持する。
- 保存完了を確認してから、既存の成功時処理で入力欄や画面を切り替える。
- 数百行の理由をalertに連結せず、件数と上限付きの代表例を表示する。
- 保存結果不明・保存済みだが画面反映に失敗した場合の再送防止は維持する。

### 5.2 更新確認

EventUpdateDiffに、通常の行除外を伝える任意の診断情報を追加する。既存のcsvReviewと区別する。

診断情報は、sheetImport.tsの解析結果からupdateFlow.ts、EventUpdateDiff、pendingEventUpdate.diff、AppOverlayLayer.tsx、UpdateConfirmationModal.tsxの順に引き継ぐ。現在のAppOverlayLayer.tsxは差分の各項目を個別のpropsとして渡しているため、新しい診断情報も明示的に渡す作業を含める。

- 通常のシート更新と更新元切替の両方で、同じ診断情報を表示する。
- 中継・表示では解析や全品目の再集計を行わず、解析時に作った集計と上限付き代表例を参照する。
- モーダル内の対応関係の選択による差分再計算でも診断情報を保持する。数量の再確認・確認画面の再開では、実際に確認する更新候補と診断情報を一致させる。
- 診断情報がない既存の呼出しは従来どおり動作させる。キャンセル後や次の取込に、前回の診断情報を残さない。

既存の更新確認画面に、次の情報をまとめて表示する。

- 取込対象になった品目数。
- 必須4項目欠落による除外件数と不足項目。
- 削除候補数と保護によって残る品目数。
- 追加・変更・削除の既存の差分。

通常除外の情報だけではacceptCsvExclusionsを必須にしない。既存のcsvReviewが必要な場合は、その確認条件を維持する。

全行が対象外の場合も確認画面を通し、自動で削除を実行しない。削除候補・保護対象の件数を明示する。更新元の切替は、品目の更新と同じ既存の確定処理へ接続する。

### 5.3 ID・配置・購入記録の維持

- 差分計算には採用行だけを渡す。
- 一対一の照合・未解決対応の確認は既存処理を利用する。
- 残る既存品目のID、購入状態、実購入数、金額、利用者メモを不用意に上書きしない。
- 行の除外で、別品目へ購入記録や配置情報を転用しない。
- 一括取込では、6.5の参照一致と生成配列の件数・順序をID対応確定まで保持し、配置ソートはその後に行う。
- 削除後の参照整理は既存の更新処理で行い、別の削除処理を新設しない。

## 6. 任意URL・任意項目の正規化設計

### 6.1 正規形

画面の入力欄は空文字列を使用できる。完成した品目データの未入力URLは、url項目を持たない形に統一する。

| 入力・既存値                     | 正規化結果                               |
| -------------------------------- | ---------------------------------------- |
| url項目なし                      | 変更なし                                 |
| url: undefined                   | url項目を省略                            |
| url: 空文字列                    | url項目を省略                            |
| url: 空白のみの文字列            | url項目を省略                            |
| 空ではないURL文字列              | 入力経路の既存処理に従って保持           |
| 数値・オブジェクト・配列・null等 | 自動変換せず、既存検証で不正値として扱う |

空ではない既存URLを、本対応だけのために一律に書き換えない。Googleシートからの取込にあるHTTP/HTTPSの確認等は維持し、手動入力へ新しい制約を追加する変更と混在させない。

### 6.2 共通処理

新規ファイル候補：src/utils/itemOptionalFields.ts。

提案する責務：

- 単一品目の既知の任意項目を正規化する。
- 取込・復元・起動時に利用する配列・イベント別品目の正規化を補助する。
- 正規化で変更がない場合、元のオブジェクト・配列・イベント別データを返す。
- 変更がある場合だけ、対象品目と格納する枝をコピーする。
- 型と責務に応じて関数を分け、画面状態やDBへ依存させない。

品目・配列の入力を破壊しない。凍結された読込データにも適用できる純粋な処理とする。同じ結果への再適用では新しいオブジェクトを作らない。

### 6.3 URL以外の任意項目

ShoppingItemで省略可能と定義され、既存検証でも項目省略を認める既知のキーについて、値がundefinedの場合のみ項目を省略する。

対象候補：

- catalogPrice
- limitedPurchasedQuantity
- sheetRemarks
- sheetIdentityVerified
- url
- priorityLevel
- protectionLevel
- source
- assignedTo
- lastSyncedAt
- orderIndex
- postponed
- manualHallId

URL以外の空文字列は一律に削除しない。false、0、有効なnullを保持する。必須項目の欠落や型不正を、この処理で補完・隠蔽しない。未知の将来フィールドも一律に削除しない。

limitedPurchasedQuantityなど、購入状態に応じて必要となる値の条件検証は既存処理に任せる。undefinedを省略した結果、必要な値がなければ従来の検証で検出する。

### 6.4 「変更なし」と「削除」の区別

正規化は、変更指示を既存品目へ適用して完成した品目に対して行う。

1. URLを変更しない指示では、既存URLを残す。
2. 空欄にした指示では、既存のurl項目を削除する。
3. 値を設定する指示では、入力経路の処理後の文字列を保持する。

空欄を先に省略してから既存品目へ重ねる実装では、以前のURLが残る。その実装にしない。

### 6.5 編集意図・一括取込とオブジェクト参照

現行の更新処理はWeakMapに、編集開始時の基準・明示的な変更欄・限数入力の意図・対象確認情報を保持している。

正規化で入力オブジェクトをコピーする前に、元の入力からこれらの情報を取得する。既存の競合確認へ引き継ぎ、コピーによって情報を失わないようにする。

品目の配列・索引・ガード世代を再利用する既存の契約を守る。URLの変更がない購入・数量更新で、構造変更として扱われることや、高速な部分更新から外れることを防ぐ。

一括取込も参照一致へ依存する。[applyBulkAdd](../src/app/commands/useShoppingItemMutationCommands.ts)は、sourceRows[].itemをキーにしたMapからnewItemsData内の元の入力品目を引き、sourceRowIdをnewItems[index].idへ対応付ける。[ImportScreen](../src/components/ImportScreen.tsx)は同じ入力品目をitemsとsourceRowsへ登録している。

- 保存用正規化は、[buildBulkAddItems](../src/features/events/bulkAdd.ts)がID・数量・source・保護設定等を組み立てた完成品目へ適用する方法を優先する。元のnewItemsDataとsourceRowsを別々にコピーしない。
- 入力側で完成品目を正規化する必要がある場合は、正規化結果の同じ品目オブジェクトをitemsとsourceRows[].itemの両方へ登録する。入力配列だけを正規化して参照対応を失わない。
- ID対応を確定するまで、入力配列と生成品目配列の件数・順序を変えない。除外・重複解決・再試行でも元のsourceRowIdを保持し、配置用の並替えはID対応の確定後に行う。
- 参照不一致を内容キーによる再照合で補う処理や、対応のためだけの品目全体の再コピーを追加しない。未知のフィールド・購入記録・配置の既存契約を保つ。

## 7. 読込・復元・再試行・保存の整合性

### 7.1 起動時の既存データ

1. 保存内容と保存版の整合性を、既存の読込処理で確認する。
2. 元の読込結果と期待する保存版を保持する。
3. 既知の未入力表現をアプリ用データとして正規化する。
4. 正規化後の構造と参照を検証する。
5. 変更がある場合だけ、既存の原子的保存で反映する。
6. 保存成功後に最新の読込結果を取得し、画面と保存処理の基準にする。
7. 変更がなければ、正規化だけを理由とする追加保存を行わない。

現行workerの[起動時読込](../src/persistence/worker/persistenceWorkerServer.ts)は、readApplicationSnapshotにshareVerifiedとprepareScopedCommandsをtrueで渡す。[DBの読込内部](../src/persistence/db/atomicRestoreTransaction.ts)は条件により、日付レコード・sidecar・マップの保存形式を準備するため、commitApplicationSnapshotAtomicallyを実行する。この準備保存と後続のURL互換保存が、同じ初回起動で重なる可能性がある。

旧形式の整合性移行も必要な場合は、同じ原データ・保存版・検証条件を保てる既存経路の範囲で同じ保存へまとめる。移行元の原データと移行後の正規化済みデータを区別する。準備保存とURL互換保存を必ず1回にするためのDB／worker通信の再設計は今回の必須条件にしない。準備保存・検証を抑止せず、保存が分かれる場合は理由・総回数・追加時間を11.5で記録する。

上記7の「追加保存なし」はURL正規化を理由とする保存を指し、既存の読込内部の準備保存まで0回とみなさない。保存後の再読込と次回起動で、準備保存やURL互換保存が反復しないことも確認する。

期待する保存版・整合性検証用の原データを、正規化済みの値で置き換えない。保存版が変わった場合は既存の競合処理へ戻る。

互換対応の書込みに失敗した場合、元データを保持し、既存の起動・保存・復旧の処理に従って報告・再試行する。データを削除したり、保存済み扱いにしたりしない。

### 7.2 バックアップ・復元

- 既存の完全版JSON・XLSXの形式とバージョンを維持する。
- 読取後、アプリ用の構造検証へ渡す前に同じ正規化規則を適用する。
- 出力する品目も同じ正規形にする。
- 既存の未知フィールドの互換性・参照修復・設定復元を維持する。
- 表取込の必須4項目判定を、完全版復元へ適用しない。
- 正規化のための新たな全文JSON往復を追加しない。既存のシリアライズの責務は維持する。

### 7.3 保留操作

- 再計画時、対象品目の未入力表現を同じ規則で正規化する。
- 操作ID、順番、編集基準、意図した変更を保持する。
- 対象の削除・所属変更・予定数量変更等の既存の有効性確認を通す。
- 確認内容が変わった場合は既存機構で再確認する。
- 保存成功後にだけ、対応する保留状態と失敗表示を解消する。
- 実際のDB失敗・容量不足等による保留は維持する。

通常操作の高速経路へ、保留互換対応のための全件処理を追加しない。再試行時の互換処理は、対象の操作と変更対象に限定する。

同一セッション内の再試行と、バックアップからの復元を分けて検証する。既に動作中の旧版PWAの未保存メモリが、コード更新・再読込だけで自動的に引き継がれる前提は置かない。既存の更新保留・バックアップ・復元の仕組みを利用する。

### 7.4 同じデータを確認・保存・画面反映に使う

確認内容と保存対象を確定する前に正規化し、同じ結果を保存後の画面反映に使う。

worker側だけ、またはDBへの書込み直前だけで、呼出し元に返さずデータを変更する構成にしない。現行は呼出し元のsnapshotを保存後に採用する経路があるため、画面・workerのミラー・永続データを一致させる。

構造検証と参照検証は、データを書き換えない処理として維持する。CAS、イベント世代、確認token、変更箇所だけの保存を迂回しない。

### 11.2 合格基準

- 96個の条件・操作の組すべてで、中央値55.0ms以下。
- 同じすべての組で、95%点100ms以下。
- 同じすべての組で、20サンプル以上。
- 条件をまとめた平均値で、遅い条件を相殺しない。
- 保存完了時間は操作反応と分けて記録する。
- CPUプロファイル付き診断測定は、通過判定用のサンプルと分ける。
- 起動時の初回互換対応、取込・復元の完了時間も、通常操作の反応時間と分ける。
- 1,500品目の未測定を今回の未完了理由にしない。
- 1,500品目も通過したという主張を今回の結果に追加しない。

この絶対基準の判定に加え、11.4の変更前後比較を行う。55.0ms／100ms以内であっても、再現する性能悪化を見逃さない。取込・起動時互換対応・復元・再試行の完了時間には、この買い物操作用の閾値を流用せず、11.5の経路別測定で増減を確認する。

スマートフォンのレイアウトをPC上のブラウザーで測定した場合、実機測定とは区別して記録する。

### 11.4 同じ環境・入力での変更前後比較

1. アプリの変更前ソースを固定し、コミット・未コミット差分、固定入力の内容とハッシュ、測定手順を保存する。同じPC・OS・ブラウザー・Node.js・依存関係・ビルド設定・画面幅・保存方式を使い、IndexedDB直接実行とworker実行を混ぜて比較しない。
2. 比較用の測定コードを追加する場合は、同じコードを前後に適用する。アプリ本体の変更を含まない変更前のビルドと、変更後のビルドを別々に作る。別のソースのビルドや稼働中の開発サーバーを誤って測らない。
3. 変更前後の各測定セッションを同一の保存データ・イベント・保留操作・入力から開始し、セッション内の操作列と繰り返し順序を揃える。11.5の独立試行は毎回同じ初期状態へ戻す。初期化や障害注入などの準備時間は測定区間から分ける。履歴・地図の負荷、変更対象数、除外行の割合、保留件数を前後で変えない。
4. 11.1の全96組と11.5の比較可能な経路別ケースについて、前後それぞれ20サンプル以上を採る。買い物操作は既存テストの測定区間・操作列・集計方法を維持する。ウォームアップの扱いを揃え、初回処理と再実行・キャッシュ利用時を区別する。1 workerで測り、CPUプロファイル・別の性能測定を同時実行しない。
5. 同じ条件ごとに、前後のサンプル数・中央値・95%点、差分ms、増減率を並べる。増減率（%）は（変更後－変更前）÷変更前×100とし、変更前が0なら算出せず差分msを使う。遅い条件を全体平均や改善した条件で相殺しない。
6. 変更前を複数回測って実測のばらつきを記録する。それを超える悪化があれば同じ条件で前後を交互に再測定し、全件正規化・コピー・再解析・保存回数・再描画の増加を調べる。今回追加した不要な処理を減らして再測定し、再現する悪化を未解決のまま性能維持済みと扱わない。

   55.0ms／100msの絶対基準と、変更前後の比較評価は別々に記録する。比較のために絶対基準を緩めたり、測定後に都合のよい許容率を設定したりしない。初回互換対応で必要な追加処理が残る場合も、その時間と追加保存回数、影響するケース、通常起動では繰り返さないことを記録し、悪化がないという結論と区別する。

### 11.5 直接変更する経路の測定

150・500品目の両方で次を測る。各入力形式・初回／再実行・保存方式の比較対象を固定し、前後で正常完了を比較できるケースはそれぞれ20サンプル以上を採る。変更前に正常完了できない仕様変更ケースは比較不能として分け、変更後の完了時間を20サンプル以上記録する。買い物操作の8プロファイルを機械的に全経路へ掛け合わせる必要はなく、経路に関係する条件を明示して比較する。

| 経路           | 固定する主なケース                                                                     | 測定区間・内訳                                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 取込           | シート新規作成・通常更新・更新元切替。既存で成功する正常行、欠落行混在、全行除外を区別 | 取込開始から新規保存・画面反映完了、または診断付き更新確認の表示まで。更新確定から保存・画面反映完了も別測定。CSV受信後の解析・差分生成・表示時間を区分 |
| 起動時互換対応 | 保存形式準備とURL互換対応の要否、両方が必要な旧データ、次回起動（B01〜B06）            | 起動開始から操作可能な画面まで。読込内部の準備保存・正規化・検証・互換保存・再読込・画面反映を区分し、下位処理を含む総保存回数も記録                    |
| 復元           | 同じ完全版JSON・XLSX。URL未入力の有無を含み、品目・設定・履歴・地図を固定              | 復元開始から保存・画面反映完了まで。ファイル読取・解析・正規化・検証・保存を区分                                                                        |
| 再試行         | 同じ保存失敗を起こし、同じ保留操作と順序を用意。単一操作と後続編集がある状態を区別     | 再試行開始から再計画・必要な再確認の表示まで。確認後から保存・画面反映完了も別測定。人の確認待ち時間は処理時間へ含めない                                |

起動時は次の固定ケースを150・500品目の両方で測る。保存形式の準備要否は、日付レコード・sidecar・マップの保存制御情報まで含めて固定する。初回の独立試行は毎回同じ移行前データへ戻し、次回起動と混ぜない。

| ケース | 初期状態                                                    | 確認・測定すること                                                             |
| ------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------ |
| B01    | 保存形式の準備済み・URLも正規化済み                         | 今回の対応による追加保存なし。通常起動の時間と読込回数を変更前後比較           |
| B02    | 保存形式の準備だけが必要・URLは正規化済み                   | 既存の準備保存を総回数へ含め、URLを理由とする保存を追加しない                  |
| B03    | 保存形式は準備済み・URL互換対応だけが必要                   | 必要な互換保存と再読込を測り、無変更保存・正規化の反復を増やさない             |
| B04    | 保存形式の準備とURL互換対応が両方必要                       | 読込内部の準備保存と後続の互換保存を含む総回数・総時間・各処理の内訳を記録     |
| B05    | B04の対応完了後の次回起動                                   | 準備・URL互換対応を理由とする追加保存がなく、毎起動反復しない                  |
| B06    | B04の準備保存または互換保存で失敗・競合し、既存経路で再試行 | 失敗・再試行の回数と区間を分け、原データ・保存版・完了後の画面と保存内容を確認 |

- B04のworker用fixtureはeventConsistencyが存在し、復旧候補がなく、認証済みroot／scopeReady等が未準備で、実際にreadApplicationSnapshot内部の準備保存条件を満たすものとする。単なる旧データという名称やUI側の保存モックだけで条件充足としない。正常完了を前後比較する共通入力には空文字列URLを用い、旧版で起動に失敗するundefinedは別ケースとして記録する。
- 保存回数は、起動開始から操作可能になるまでの準備保存・旧整合性移行・URL互換保存・再読込時の保存を含む。下位の原子的保存で総試行数・成功コミット数・失敗／競合再試行数を観測し、同じ物理コミットを上位呼出しと下位処理で二重計上しない。各storeへの書込要求数はコミット数と分ける。
- 読込時間には内部の準備保存を内訳として含める。総時間を算出する際、親の読込時間へ内部保存時間を重ねて加算しない。保存をまとめられない場合の理由と追加コストを残し、安全な既存保存経路を維持する。
- 計測はテスト用の観測で行い、通常操作へ常時ログ・追加走査を持ち込まない。IndexedDB直接実行・worker実行は同じ方式同士で比較する。
- シートの通信は同じ固定CSV応答を使い、外部回線の揺れを処理時間の増減と混同しない。通信を含む全体時間と受信後の処理時間を区別する。
- 正規化済みデータでは、URL互換対応を理由とする追加保存がないことを確認する。保存形式の準備が残るB02と、準備も完了したB01・B05を区別し、既存の準備保存まで0回とみなさない。
- 復元と再試行は、既存のIndexedDB直接実行・worker実行をそれぞれ同じ方式同士で比較する。通常の購入・数量更新に全件処理や全体保存が増えていないことも併せて確認する。
- 変更前に失敗する入力では、失敗までの短い時間と変更後の正常完了時間を同等な処理として比較しない。旧実装でも成功する共通入力で前後比較し、仕様変更ケースは変更前の到達点・失敗理由と変更後の所要時間を別記する。比較不能を0msや性能維持として扱わない。
- 経路別の測定で繰り返す正規化・追加保存・不要な再描画が見つかった場合は、適用位置や対象範囲を見直す。初回だけ必要な処理の追加コストも記録し、通常操作へ持ち込まない。

## 12. 性能を保つ実装上の制約

| 領域                 | 制約                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| 通常の追加・編集     | 対象品目を中心に処理し、無関係なイベントや地図を走査しない           |
| 購入・数量の部分更新 | 既存の索引・差分更新・対象確認を維持                                 |
| 未変更の品目・行     | オブジェクト参照を保持し、不要な再描画を誘発しない                   |
| シート取込           | 既存の解析・変換ループで診断情報を集計                               |
| 起動・復元           | 対象全体の互換対応を通常操作と分離し、同じデータを繰り返し処理しない |
| 保存・worker         | 通常保存の入口で全snapshotを複製・正規化する処理を追加しない         |
| 診断表示             | 件数と上限付き代表例を使い、大量のDOMや長大なalertを生成しない       |
| 診断情報の中継       | 既存の集計をpropsで渡し、表示時の再解析・全件再集計を追加しない      |
| キャッシュ           | 元データの不変性と保存版を守り、古い結果を再利用しない               |
| メモリ               | 全履歴の複製や無制限の強参照キャッシュを追加しない                   |

URL変更がない操作について、現在の部分更新が構造変更・全体保存へ切り替わっていないことをテストで確認する。変更内容がない場合の不要な保存・確認画面を増やさない。

| 入力コピーでWeakMapの編集意図が失われる                | 元入力から先に情報を取得し、既存コマンドへ保持          |
| 一括取込のコピーでsourceRowsの参照一致が失われる       | 同じ入力参照と生成順を保ち、完成品目を正規化            |
| 数量不正行の先行除外でURL補完結果が変わる              | 欠落行だけを補完対象から除き、補完後に数量判定          |
| 読込内部の準備保存を数え漏らす                         | B04で下位保存を含む総回数・時間を確認                   |
| 保存先だけで変換すると画面ミラーと不一致になる         | 確認前の正規化結果を保存・画面反映で共用                |
| 起動時の構造検証が旧undefinedを拒否する                | 物理整合性確認後、構造検証前に既知の表現を統一          |
| 互換対応後も古い保存版を使う                           | 保存後に最新の読込結果を取得し、基準を更新              |
| 任意値を広く削除するとfalse・0・nullや未知項目を失う   | 既知キーのundefinedとURLの空欄だけを対象にする          |
| 行除外後に番号を振り直すと配置や診断がずれる           | sourceRowId・物理行番号を保持                           |
| 完全版復元へ4項目の条件を広げると手動品目を失う        | 表取込と完全版復元の責務を分離                          |
| 通常操作で全件正規化すると反応が遅くなる               | 共通生成・更新経路に集約し、通常は変更対象だけ処理      |
| 既定の性能コマンドに1,500品目が含まれる                | --listで対象16件を確認し、絞ったコマンドを使う          |
| 絶対基準内の性能悪化や初回以外の互換処理の反復を見逃す | 同じ環境・入力で前後比較し、4経路の時間と保存回数も確認 |
