# 操作応答速度の改善

編集・実行・集中モード、マップ切り替え、アイテム編集などで共有する状態更新・表示用変換・保存処理を最適化した。既存の確認操作、保存失敗時の再試行、他タブとの競合検出、データ形式を維持している。

## 同条件での実ブラウザー計測

Windows 11、Node 24.19.0、Playwright 1.62.1 の headless Chromium、1280×900、150アイテム、100×100のマップ（1万マス）、1イベント・1日・1ホール。各ビルドで新しいブラウザーを起動し、同じバックアップを公開UIから復元した。比較先→修正前→修正後の順に実行し、CPUプロファイラーを有効にして3周測定した。別のテストやビルド処理との同時実行は避けた。

単位はms、数値は中央値。実行モードへの遷移は1周に2回、その他は1周に1回。初回の遅延読み込みも含む。操作開始から対象の表示変更を確認し、2回の `requestAnimationFrame` 後までを計測した。入力欄は既存の楽観表示で更新されるため、これは画面応答時間である。

編集モードは約39%、集中モードは約33%、数量変更は約58%、金額変更は約31%、購入状態変更は約51.5%短縮した。比較先との差は、集中モード約22ms、金額変更約13ms、購入状態変更約9ms。全操作・全データ量・全端末の時間を保証する測定ではなく、共通処理の改善を確認するローカル診断である。

[実測サンプルと計測条件](interaction-performance.samples.json) に90件の値を保存している。

## 実装

- 状態が変わらない描画では、表示用の整合性変換を再実行しない。イベント・マップ・ホール・所属情報の変更時には再計算する。
- 購入情報の変更では、所属情報と変更していないカードの参照を再利用する。イベント・日付・プロパティの並び順も保持する。
- マップ内の番号検索を、その処理内で索引化して繰り返しの全件検索を減らす。
- 同じ変更計画内で表示用変換を共有し、アプリ内の変更で編集対象でないマップを読み取り専用として再利用する。マップ編集と通常の公開呼び出しではコピーによる分離を維持する。
- 保存済みの全領域に対する競合検査を続け、更新した領域だけを確定する。変更のない確定操作でも軽量な領域を保存し、保存失敗・再試行の動作を保つ。初期化・移行・復元では従来の全領域保存を使う。
- ハッシュのFNV-1A-64計算を32ビット整数2個の演算に変更する。BigIntによる従来の計算と同じ値を生成し、SHA-256、検査内容、保存形式を保つ。
- 正規化文字列の作成では、項目名の変換を処理内で再利用し、一時配列とコールバックの生成を減らす。

## 再計測

各PowerShellで `AGENTS.md` のUTF-8コンソールラッパーを適用する。1つ目のターミナルでアプリをビルドして起動する。

```powershell
npm run build:app
node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 4177
```

別のターミナルで測定する。独立したブラウザー内の検証用イベントを使う。

```powershell
node scripts/performance/interactionLatency.mjs http://127.0.0.1:4177
```

比較先にはGit履歴がないため、比較用のローカルビルドでは主ディレクトリのGit情報を使用した。実行したアプリは比較先のソースからビルドしたもの。この計測はリリース承認用の性能証跡には使用しない。

`npm run build:release-a` の最終リリース判定は、未コミットの変更がある状態（`sourceState=dirty`）を既存の検証規則で拒否する。アプリ本体の `build:app` は成功している。
