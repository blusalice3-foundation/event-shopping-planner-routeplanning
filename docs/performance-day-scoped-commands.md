# イベント・日付単位の高速化と検証

2026-10-09。モード変更と訪問先編集では、対象イベント・日付の差分コマンドを永続化Workerへ送り、最新の保存状態に適用する。画面には変更した枝を返す。未変更の過去イベント、別日付、マップの参照を保持する。

## 保存範囲

[日付差分コマンド](../src/features/consistency/domain/dayMutation.ts)の`ApplicationDayMutation`はモード指定、または日付単位の変更前・変更後を受け付ける。既存の訪問先操作がまとめて変更する実行ID、ホール別訪問先、保存ルート、整合性情報は同じIndexedDBトランザクションで確定する。対象日付の投影と整合性検査を再利用し、未変更の検証済みマップ形状の再走査を省く。

[永続化層](../src/persistence/db/atomicRestoreTransaction.ts)はWorkerが所有する検証済みスナップショットを再利用する。全storeのrevision、メタデータのハッシュ・スキーマ、checkpoint、イベント世代、移行記録・保全記録、実行時復旧候補が一致する場合だけ再利用する。読み取りと書き込みの両方で確認し、更新競合があれば最新状態を読み直して最大3回再試行する。別タブによる削除・置換、競合する訪問先変更、重複日付、未処理の旧データは既存の全体検査・確認経路へ戻す。保存失敗時は既存の保留・再試行処理を使う。

このキャッシュは、revisionとcheckpointを同時に更新するアプリの永続化APIを経由した書き込みを前提にする。任意の外部コードによるIndexedDBペイロードだけの直接書き換えはキャッシュ利用条件外。通常の全体読み取り・復元・品目編集では従来の全store検証を維持する。温まった日付コマンドで`get("data")`とcursor読込が0回であることをWorkerテストで確認するため、今回イベント単位のDBレコード分割は行っていない。変更storeの保存形式は従来どおり。

## 描画とマップ

挿入案内、キャンセル、重複候補の選択はキャンバス外に置く。実ポインターで番号1〜5を選択し、案内領域がキャンバスと重ならないことを検査する。

位置検索にはマップ参照ごとの索引を使い、番号重複の曖昧判定を維持する。挿入選択用の防御的マップ複製も同一参照ごとに一度だけ作る。閉じた訪問先パネルの位置検索を止め、無効な経路要求ではキー生成、Worker起動、送信を止める。無効化時に実行中Workerを終了し、古い結果を破棄する。集中モードのマップを表示したときに必要な探索を開始する。

一覧では保持した高さと親一覧の位置から表示候補を推定し、表示範囲±500pxだけを同期位置計測する。他の行はIntersectionObserverが更新する。高さキャッシュはObserver登録とは別に保持し、行ID、モード・レイアウト、一覧の幅、画面幅、アプリ・ブラウザの倍率で区別する。最大4,096件を保持する。最初のObserver通知前のアンカー取得は画面内のヒットテストで範囲を絞る。

## JSONバックアップ

[専用Worker](../src/persistence/worker/backup.worker.ts)がIndexedDB取得、移行、修復、正規化、検証、JSON生成を行い、Blobを返す。通常はUIから全体スナップショットを転送しない。未保存の受理済み編集だけをイベント単位で渡し、書き出すデータに反映する。バックアップ生成の待機中も永続化コマンドのキューを開放する。実行時復旧候補がある場合やIndexedDB取得が失敗した場合は、受付時の画面状態をWorkerへ渡して書き出す。

内部で生成・検証したバックアップのJSON生成では、公開serializerによる再移行・再修復・再検証を省く。外部JSONの読み込み検証と公開serializerの検査は維持する。

## 計測条件

Windows、Playwright Chromium、ヘッドレス、1280×900。アクティブ500品目、40,000セル。過去なし／10,000件（10イベント）の両方で、実際の復元UIを使って全イベントを復元し、IndexedDBの件数を確認する。変更前はコミット`8ae2d7c2ad093b2282e26b140aaf0267d56d1e5f`、変更後は今回の作業ツリーをそれぞれ`build:app`でビルドする。

React profiler、位置計測の差し替え、アプリへの時間計装は使わない。モードボタンへの実`mouse.click`イベント時刻から、選択状態が更新されて2回のrequestAnimationFrameを経過するまでを測る。各条件3つの独立セッション、各セッション各6方向30回。セッションの最初の実行→編集と各方向の初回を再操作から分離する。バックアップの総時間とメインスレッドLong Task、訪問先編集の画面反映・IDB保存・最新対象を含む経路完了は別々に記録する。訪問先の保存・経路測定値にはPlaywright確認とIDBポーリングの遅延が含まれる。

数値はこの開発機での結果であり、実端末の保証値ではない。中央値200ms、p95 300ms、過去10,000件による中央値増分30msは引き続き実端末で確認する開発目標とする。

## 訪問先編集とバックアップの実測

500品目＋過去10,000件、初期訪問先5件。各番号1〜5へ1回ずつ挿入して解除し、各回の再読込で保存状態を確認した。全20操作で永続化Workerへの送信は`day`だけで、全体スナップショットの`commit`は0回だった。罫線・色付き条件には2ホールを設定し、西ホールを選択する。地図は40,000セル、色付きセル・罫線の障害物規則を維持し、訪問先周辺に通路を確保する。

## 回帰検証

単体・統合・Workerは219ファイル・2,370テストが成功。ブラウザーは既存経路の103ケースとモード計測6ケース、訪問先2ケース、バックアップ1ケースを確認した。複数タブの競合、イベント置換による世代更新、重複日付の再確認、保存失敗時の保留・取消・再試行、日本語の未保存入力を含むバックアップ、複数ホール、集中セルを含む。

一覧は500件・1,500件で初期行位置の同期計測20回未満を検査し、検索移動、前後の訪問先移動、PC・スマートフォン表示、Tab移動、ドラッグ、印刷、表示倍率変更時の位置保持、非表示マップを再表示した後の描画を確認した。競合注入はrevisionのCAS読取時に行い、保存範囲はトランザクションに含まれるstore名ではなく実際のペイロード書込で検査する。

型検査、ESLint、整形、アーキテクチャ境界、テスト分類、DB互換性、文字コード、`git diff --check`を確認した。ローカルアプリビルドは成功。未コミットの作業ツリーでの検証で、本番公開はしていない。ESLintでは検証用の一時ディレクトリを`--ignore-pattern '**/.tmp*/**'`で除外する。

既存ファイルのUTF-8、BOM有無、改行コードを維持。追加ファイルはUTF-8（BOMなし）・LF。保存後に再読込し、「ユーザー登録」「エラーが発生しました」、U+FFFD、不自然な`?`、BOM、改行だけの差分を確認した。

## 再実行

```powershell
npm run build:app
npx playwright test tests/browser/responsive-performance.spec.ts --grep 'six mode transitions' --workers=1 --reporter=json
npx playwright test tests/browser/responsive-performance.spec.ts --grep '@visit-performance|@backup-performance' --workers=1 --reporter=json
```

`mode-response-timings`、`visit-response-timings`、`backup-response-timings`添付に生の測定値を保存する。比較対象のビルドを別ポートで起動する場合は`PLAYWRIGHT_BASE_URL`を指定する。
