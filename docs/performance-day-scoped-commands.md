## 保存範囲

[日付差分コマンド](../src/features/consistency/domain/dayMutation.ts)の`ApplicationDayMutation`はモード指定、または日付単位の変更前・変更後を受け付ける。既存の訪問先操作がまとめて変更する実行ID、ホール別訪問先、保存ルート、整合性情報は同じIndexedDBトランザクションで確定する。対象日付の投影と整合性検査を再利用し、未変更の検証済みマップ形状の再走査を省く。

[永続化層](../src/persistence/db/atomicRestoreTransaction.ts)はWorkerが所有する検証済みスナップショットを再利用する。全storeのrevision、メタデータのハッシュ・スキーマ、checkpoint、イベント世代、移行記録・保全記録、実行時復旧候補が一致する場合だけ再利用する。読み取りと書き込みの両方で確認し、更新競合があれば最新状態を読み直して最大3回再試行する。別タブによる削除・置換、競合する訪問先変更、重複日付、未処理の旧データは既存の全体検査・確認経路へ戻す。保存失敗時は既存の保留・再試行処理を使う。

このキャッシュは、revisionとcheckpointを同時に更新するアプリの永続化APIを経由した書き込みを前提にする。任意の外部コードによるIndexedDBペイロードだけの直接書き換えはキャッシュ利用条件外。通常の全体読み取り・復元・品目編集では全store検証を維持する。

追加実装では、`dayModes`、`executeModeItems`、`hallRouteSettings`、`routeSettings`、`eventConsistency`をイベント・日付別レコードへ分割した。[保存形式](../src/persistence/db/dayRecordStorage.ts)はイベント共通情報と各日付のレコード、および件数・集約チェックサムを含む小さな`data`ヘッダーで構成する。各レコードのSHA-256はstore・キー・値を結び付け、全体読込では全レコードとヘッダーを検証する。再操作は変更した日付だけを複製・ハッシュ・書き込みし、過去イベントや別日付の値を再保存しない。変更前の個別ハッシュを使って集約チェックサムを差分更新するため、全レコードの比較・走査も不要になる。

変更レコード、ヘッダー、revision、checkpointは関連storeを含めて同じトランザクションで保存する。個別レコードのキャッシュはトランザクション成功後に更新し、保存失敗・取消時は元のキャッシュを維持する。対象外イベント・日付・storeへの変更は保存前に拒否する。旧形式は最初の日付保存時に一度だけ検証済みデータから変換する。この初回変換と、全体復元・構造変更・キャッシュ失効後の再検証には全体処理が必要だが、通常の再操作では行わない。

DBバージョンは9とし、8以前のクライアントによる新形式への書き込みを防ぐ。旧形式の読込、全量取得API、全体保存API、復旧候補の採用、JSONバックアップは論理的な従来のデータ形状を維持する。個別レコードが破損・欠落した場合は自動採用せず、ヘッダーと物理レコードを復旧証拠として保全する。ヘッダーの世代情報だけが壊れ、個別レコードを検証できる場合は、利用者が選択した論理データを採用できる。

UIの4種類の日付storeのfunctional setterは、変更前storeを丸ごと`structuredClone`せず、通常のReactの不変更新契約で変更した枝だけを作る。表示用の投影も未変更イベントの訪問先・モードの枝を再利用する。過去10,000件を含むWorkerテストで、温まった日付操作の`get("data")`・cursor読込が0回、書込が対象イベント・日付と250文字未満のヘッダーだけであることを確認する。UIテストでは、旧storeの全体複製が呼ばれず、未変更の過去イベントの参照が保持されることを確認する。

## 描画とマップ

挿入案内、キャンセル、重複候補の選択はキャンバス外に置く。実ポインターで番号1〜5を選択し、案内領域がキャンバスと重ならないことを検査する。

位置検索にはマップ参照ごとの索引を使い、番号重複の曖昧判定を維持する。挿入選択用の防御的マップ複製も同一参照ごとに一度だけ作る。閉じた訪問先パネルの位置検索を止め、無効な経路要求ではキー生成、Worker起動、送信を止める。無効化時に実行中Workerを終了し、古い結果を破棄する。集中モードのマップを表示したときに必要な探索を開始する。

一覧では保持した高さと親一覧の位置から表示候補を推定し、表示範囲±500pxだけを同期位置計測する。他の行はIntersectionObserverが更新する。高さキャッシュはObserver登録とは別に保持し、行ID、モード・レイアウト、一覧の幅、画面幅、アプリ・ブラウザの倍率で区別する。最大4,096件を保持する。最初のObserver通知前のアンカー取得は画面内のヒットテストで範囲を絞る。

## JSONバックアップ

[専用Worker](../src/persistence/worker/backup.worker.ts)がIndexedDB取得、移行、修復、正規化、検証、JSON生成を行い、Blobを返す。通常はUIから全体スナップショットを転送しない。未保存の受理済み編集だけをイベント単位で渡し、書き出すデータに反映する。バックアップ生成の待機中も永続化コマンドのキューを開放する。実行時復旧候補がある場合やIndexedDB取得が失敗した場合は、受付時の画面状態をWorkerへ渡して書き出す。

内部で生成・検証したバックアップのJSON生成では、公開serializerによる再移行・再修復・再検証を省く。外部JSONの読み込み検証と公開serializerの検査は維持する。

## 再実行

```powershell
npm run build:app
npx playwright test tests/browser/responsive-performance.spec.ts --grep 'six mode transitions' --workers=1 --reporter=json
npx playwright test tests/browser/responsive-performance.spec.ts --grep '@visit-performance|@backup-performance' --workers=1 --reporter=json
```

`mode-response-timings`、`visit-response-timings`、`backup-response-timings`添付に生の測定値を保存する。比較対象のビルドを別ポートで起動する場合は`PLAYWRIGHT_BASE_URL`を指定する。
