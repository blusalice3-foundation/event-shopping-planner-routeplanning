# ダイアログの画面超過・スクロール不能を解消する実装方針

作成日: 2026-11-12。状態: 対象ダイアログの製品実装・自動検証記録の作成済み。実機のキーボード・IME・browser/PWA別受入と正式性能判定は未実施。実装台帳と検証範囲は末尾の実施記録を参照。

変更前ソース: `bcf1c2d98a30e02867e735ece3e1100e72a08fb0`。根拠: [事前調査と再現画像](../artifacts/dialog-overflow-investigation-20261112/investigation.md)。本書は、Windows・Android・iOSで内容と操作へ到達できるようにし、既存の正常な動作と通常操作の軽さを維持するための作業仕様である。

**採用する対策**

対象のダイアログだけに共通の外部CSSを明示適用し、画面内に高さを制限した本体をネイティブスクロールできるようにする。通常サイズで収まるときは、現在の幅・内容に応じた高さ・中央配置を維持する。モバイルのソフトキーボードは別の問題として扱い、入力のある対象画面の表示中だけ可視領域に合わせる補正を加える。

初回はダイアログ全体をスクロールの基礎とする。見出しや確定ボタンの常時固定は採用しない。固定領域だけで小さな画面を使い切ることや、sticky要素が入力・最終行を覆うことを避け、先頭から末尾の操作まで必ず到達できる方式を優先する。既存の地図取り込み等で正常に機能している本文スクロール・固定操作領域は維持する。

**CSSの共通仕様**

新規 `src/styles/dialog-layout.css` を `src/styles/application.css` から読み込み、`esp-dialog-viewport` と `esp-dialog-panel` を対象にだけ付ける。共通化するのは表示領域への制約であり、Reactの大きな共通Dialogコンポーネントへの置換は行わない。

- 外枠は現在と同じ固定配置・中央配置を維持し、高さは `100vh` をフォールバック、対応環境では `100dvh` を使用する。
- 外枠の `box-sizing:border-box` と確定した高さを前提に、本体の最大高さを外枠の内容領域の100%にする。`min-height:0`、`min-width:0` を設定する。既存の最小幅が必要な画面は、専用規則で安全な表示幅以内の最小幅を維持する。
- 本体に `overflow-y:auto` を設定し、先頭・すべての入力・注意事項・末尾の操作を同じ到達可能な範囲に置く。画面に収まるときはスクロールバーを出さない。
- 外枠余白は現在値を基本に、上下左右のsafe areaを下回らない値にする。既存の `p-4` と `mx-4` を重ねて二重に余白を設けない。元の余白が違う画面は個別の値を維持する。
- 操作ボタン、ラジオの説明、注意事項、長い対象名は、幅不足時に折り返せるようにする。入力値の省略や注意事項の件数制限で収めない。ネイティブ入力内のキャレット移動・横スクロールは維持する。
- 本体を背景へのスクロール連鎖の最終境界とする。`overscroll-behavior-y:contain` を本体に限定して使用し、非対応環境も既存のスクロールロックと実機検証で確認する。
- タッチ操作を独自のドラッグスクロールへ置き換えない。`touch-action:none`、全画面の `touchmove.preventDefault()`、一律の `pan-y` によるピンチ抑制を追加しない。
- タッチで使う確定・取消・選択行は、既存の対象領域を狭めず、変更対象の主要操作は44 CSS px以上を設計目標にする。隣接する操作の間隔を確保し、幅不足時は折り返す。44pxは本計画の操作性上の設計目標である。[W3Cのターゲット寸法の説明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

中心となるルールは以下。実装時は各画面の現在の余白・幅・ボタン領域と統合し、既存のクラス指定との競合を残さない。

```css
.esp-dialog-viewport {
  box-sizing: border-box;
  height: 100vh;
  padding: 1rem;
  padding-top: max(1rem, env(safe-area-inset-top, 0px));
  padding-right: max(1rem, env(safe-area-inset-right, 0px));
  padding-bottom: max(1rem, env(safe-area-inset-bottom, 0px));
  padding-left: max(1rem, env(safe-area-inset-left, 0px));
}

@supports (height: 100dvh) {
  .esp-dialog-viewport {
    height: 100dvh;
  }
}

.esp-dialog-panel {
  min-height: 0;
  min-width: 0;
  max-height: 100%;
  overflow-y: auto;
  overscroll-behavior-y: contain;
  overflow-wrap: anywhere;
}
```

既存の `fixed/inset-0/flex/items-center/justify-center`、幅・角丸・配色・z-indexは各画面側で維持する。`role=dialog` の要素が外枠になっている限数入力などでは、本体に相当する内側へ `esp-dialog-panel` を付ける。ARIA属性やrefをCSS都合で無差別に移動しない。safe areaと通常余白は別の制約であり、アプリ全体の `viewport-fit=cover` を追加する変更は本対策へ混ぜない。[WebKitのsafe area解説](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)

**具体化1: イベント操作メニューの幅・折返し・スクロールの統合**

`EventListScreen.tsx` の操作メニューだけに次を適用する。イベント一覧の行や他画面の見出しには適用しない。短い名称では現在の内容に応じた幅を保ち、長い名称では全文を折り返して本体内をスクロールする。

- 外枠へ `esp-dialog-viewport esp-event-menu-viewport`、本体へ `esp-dialog-panel esp-event-menu-panel` を追加する。外枠の通常余白は現行の0を維持し、各辺のsafe areaだけを確保する。共通の1remに追加して余白を重ねず、新しい `mx-*` も付けない。
- 本体の `min-w-[280px]`、`max-w-[90vw]`、`overflow-hidden` は削除し、幅の制約を下記の専用規則へ集約する。現在の `width:auto` による内容依存の幅を維持し、`w-full` や固定幅へ変更しない。通常は最小280px・最大90vwを保ち、安全領域またはブラウザ拡大後の表示幅が不足するときだけ最小幅も縮める。
- 見出しの `truncate` を削除して `esp-event-menu-title` を付ける。省略記号、行数制限、見出しだけの高さ制限を設けない。各操作の文字spanへ `esp-event-menu-action-text`、アイコンへ `shrink-0` を付け、文字だけが必要に応じて折り返すようにする。文字の複数行表示は左揃えにし、現在のpadding・アイコン間隔・主要操作の対象領域を維持する。
- 本体全体の縦スクロールで、見出し、操作一覧、末尾のキャンセルへ到達させる。横にはみ出した内容を隠すことだけで適合したように見せない。角丸・配色・枠線・z-index・ARIA・refと、操作・外側クリック・キーボードの既存ハンドラは維持する。

次の静的な専用規則を共通規則の後に置く。二つのクラスを組み合わせた指定で共通の `min-width:0` 等より優先させ、既存の競合するutilityは上記のとおり取り除く。

```css
.esp-dialog-viewport.esp-event-menu-viewport {
  padding: 0;
  padding-top: env(safe-area-inset-top, 0px);
  padding-right: env(safe-area-inset-right, 0px);
  padding-bottom: env(safe-area-inset-bottom, 0px);
  padding-left: env(safe-area-inset-left, 0px);
}

.esp-dialog-panel.esp-event-menu-panel {
  min-width: min(280px, 90vw, 100%);
  max-width: min(90vw, 100%);
}

.esp-event-menu-title,
.esp-event-menu-action-text {
  min-width: 0;
  white-space: normal;
  overflow-wrap: anywhere;
  text-align: left;
}
```

合否は以下で判定する。通常サイズの短い名称では、変更前後の本体幅と左右の中央位置の差を1 CSS px以内とし、フォント・表示倍率・使用可能な操作を同じ条件にする。文字拡大、長い名称の折返し、実safe areaによって必要になる差は意図した差として別に記録する。

| 条件                                                         | 確認する結果                                                                                                                                           |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1280×900・1366×768・390×844、短い名称                        | 現在の幅・左右中央位置・操作順を維持。不要なスクロールバーが出ない                                                                                     |
| 320×568・667×375、長い日本語名と空白のない英数字名、文字200% | 見出し全文が折り返され、横はみ出しがない。本体の `scrollWidth <= clientWidth + 1` を確認し、隠れた文字を残さない。先頭・各操作・キャンセルへ到達できる |
| 各操作行、長い文字列、マウス・タッチ・キーボード             | アイコンを潰さず文字が折り返され、フォーカス表示が切れない。各操作と取消を実行し、対応する遷移と終了を確認。スワイプで誤取消・誤実行しない             |
| iOS横向きの実safe area                                       | 本体がsafe areaを除いた利用可能領域に収まる。CSSでsafe areaを模した確認は補助診断として区別する                                                        |

**一覧内部に既存のスクロールがある画面**

事後通販の一覧288px、集中モードの一覧240px、地図セル編集の本文60vhなどは、外枠全体を制限できていないことが問題である。まず外枠の共通対策を加え、大きい画面で正常に機能する内部スクロールは維持する。

内部一覧へ新たなスクロール連鎖停止を付けず、一覧の末端から本体へ操作を引き継げること、一覧の外でも本体をスワイプできることをAndroid・iOSで確認する。低い画面で二重スクロールが操作の妨げになる場合は、その対象の内部一覧だけを低い表示領域で `max-height:none;overflow-y:visible` に切り替え、本体の一つのスクロールにまとめる。これは対象ごとの外観比較と実タッチ確認を通過させる。全一覧の仮想化・全件の複製描画・全画面のスクロール方式変更は行わない。

**ソフトキーボードと画面回転への対応**

`dvh` だけでキーボードによる遮蔽が解決するとは判断しない。キーボード表示時には、レイアウト領域が変わらず可視領域だけが縮む場合がある。画面回転、ブラウザのツールバー、ソフトキーボード、ピンチ拡大は分けて確認する。[Chromeのviewport解説](https://developer.chrome.com/blog/viewport-resize-behavior/)、[W3Cのviewport単位仕様](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)

入力のある対象画面には、新規 `src/hooks/useDialogViewport.ts` から、開いている専用外枠だけを登録する補正を設ける。表示中にキーボードを使わない画面には登録しない。大きい画面でのCSS基本表示を維持し、次の制約で実装する。

1. `window.visualViewport` が使えるとき、その `height` と `offsetTop` を可視範囲の補正に使用する。補正を要する差がなければCSSの高さ・位置を使う。未対応環境はCSS基本方式とネイティブの入力スクロールを使い、実機で到達性を確認する。[VisualViewportのAPI定義](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)
2. 開いている対象がある間だけ、共有した `visualViewport.resize/scroll` の監視を1組登録する。複数ダイアログで監視を重複させず、最後の対象を閉じたらリスナーと予約したrAFを解除する。閉じた後の常時監視を残さない。
3. イベント起点の更新は1rAFへまとめる。登録時の初期同期は下記の具体化2に従い、イベント待ちにしない。viewportの数値は共有して一度読み、値が変わった場合だけ対象の `top/height` を更新する。React state、全DOM走査、全品目のサイズ測定、継続するrAFループを使わない。
4. 値の反映は既存の `setRuntimeLayoutProperties` を使う。`top/height` は既存の許可プロパティに含まれるため、CSPや許可範囲を広げない。inline style、動的なstyleタグ、body/rootの高さ変更へ逃がさない。
5. 補正の所有先は、既存の動的座標規則と共用していない専用外枠に限る。`clearRuntimeLayoutProperties` は対象要素の動的規則全体を消すため、別機能が使用する要素では呼ばない。キーボード閉鎖時・補正不要時・アンマウント時は自分の補正を解除する。
6. `visualViewport.scale` が1から外れるピンチ拡大中は補正を停止し、古い補正規則も解除する。拡大を禁止したり、逆倍率で縮小したり、毎回中央へ戻したりしない。1へ戻ったときに再評価する。浮動小数点の比較には小さい許容差を用いる。
7. キーボードの開閉・回転・日本語IME入力でReactの再マウント、入力値の初期化、復元候補の再作成を起こさない。画面の高さや向きによって `key` を変えない。
8. フォーカスされた入力はネイティブの本体スクロールで表示させる。実機でそれだけでは遮蔽が残る場合のみ、フォーカス対象1要素と本体の矩形を確認し、必要な最小量だけ本体をスクロールする。windowへの一律 `scrollIntoView()` や入力のたびのスクロール補正は行わない。

**具体化2: キーボード表示済みの初期同期と登録・解除**

`useDialogViewport` は、外枠のrefが確定した `useLayoutEffect` で登録する。登録時に共有の同期処理を1回実行し、次の `resize/scroll` が来なくても現在の可視領域を反映する。例えば、入力中の親画面から子の入力画面へ進み、キーボードが出たままでも新しい画面が隠れないことを確認する。既存のフォーカスrefや初期フォーカスの契約は変更しない。

共有の登録一覧は専用要素と登録の識別情報を保持し、各対象に「未反映」「最後に反映したtop/height」「補正なし」の状態を持たせる。同期処理1回につきviewportの数値を一度だけ読み、同じ値を登録対象だけへ配る。差分判定は対象ごとに行い、共有の値が前回と同じでも新規対象の初回反映は省略しない。これらの状態をReact stateへ入れない。

| 契機                           | 処理順序                                                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最初の対象の登録               | 対象を未反映として追加し、共有のresize/scrollリスナーを各1個登録する。予約rAFがあれば取り消し、現在のviewportを読み登録対象へ同期する                            |
| 2対象目以降の登録              | 未反映の対象を追加し、予約rAFがあれば取り消して同じ初期同期を行う。既存対象は反映状態に差がある場合だけ更新する。リスナーを重複登録しない                        |
| resize/scrollの連続発火        | 未予約の場合だけ共有rAFを1個予約する。実行時に予約を空にして最新値を一度読み、対象ごとに更新または補正解除する。次のイベントがなければ再予約しない               |
| 一部の対象の閉鎖・アンマウント | cleanupが取得した要素と登録が現在の登録に一致する場合だけ一覧から除き、その要素の自分の補正規則を解除する。他の対象と共有監視は維持する。重複cleanupは何もしない |
| 最後の対象の閉鎖・アンマウント | 上記に加え、共有リスナーと予約rAFを解除し、共有の保持値を空にする。古いcleanupや予約処理が再登録後の対象を消去・更新しないようにする                             |

補正不要時、キーボード閉鎖時、ピンチ拡大時の規則解除と等倍復帰の処理も同じ同期処理を使う。初期同期のための全DOM走査、継続rAF、追加observer、入力ごとの監視は設けない。VisualViewport非対応時は登録・解除が安全に完了し、CSS基本方式と既存の入力操作を維持する。

新hookの単体・統合テストでは次を必須にする。viewportの模擬値によるテストは実機キーボードの受入とは区別する。

- キーボード表示済みの状態で登録し、その後にイベントを送らなくても初回補正される。同じviewport値で2対象目を開いても、その対象への反映を省略しない。
- イベントを連続発火しても保留rAFは最大1個で、同値のtop/heightを繰り返し書き込まない。登録時の同期が予約済みの更新を兼ねる場合は、その予約を残さない。
- 一方を閉じても他方の補正と監視が残り、最後を閉じたらリスナー・予約rAF・所有属性・動的規則が残らない。rAF実行前に閉じた場合も同様とする。
- React StrictModeで登録→解除→再登録しても、重複監視や規則の消失がなく、新しい登録へ古いcleanupが干渉しない。再表示した対象にも初回補正される。
- ピンチ開始時に補正を解除し、等倍へ戻ると再評価する。別要素が所有する動的規則を消さない。
- 回転、キーボード開閉、親子画面の切替で入力値・選択・保存状態を初期化しない。実機枠ではキーボードが残ったままの子入力画面への遷移も確認する。

固定要素の座標系が変わる祖先の `transform/filter/contain` は、補正対象を登録する前に確認する。既存のAppMainContentには表示倍率用transformがあるため、内部の座標をlayout viewportと同一視しない。現在のbody portalと外層配置を維持する。変換祖先下の対象が見つかったときだけ個別に配置を調整し、重なり・外側クリック・フォーカス復帰を確認する。全表示のportal化や全体の倍率補正は実施しない。

アプリ全体のmeta viewportへ `interactive-widget` を追加する方式、`navigator.virtualKeyboard.overlaysContent` の全体切替、ブラウザ名だけで動作を決める方式は採用しない。対象外の地図・一覧・フッターの高さや操作へ波及させない。

**既存動作を維持する境界**

**具体化3: 既存90vh入力画面のキーボード到達性と変更要否**

`ItemEditDialog.tsx` と `DuplicateEventDialog.tsx` は、既存の `max-h-[90vh]` と本体スクロールを維持して比較する。ただし、「高さ制限あり」を理由にキーボード表示時の到達性まで合格とは判定しない。製品修正を始める前に、同じfixture・端末・画面向き・文字サイズ・表示倍率・browser/PWA条件で変更前の記録を採り、変更後と対応させる。

| -------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ItemEditDialog       | 通常品目・限数品目、長いサークル名とタイトル、複数行のシート備考、所属プレビュー、保存エラー | 上段のサークル名、中段の予定・実購入数、下段の利用者メモ・URLを編集し、末尾の保存・取消を実行する。限数超過の子確認から編集へ戻る操作、保存待ち→失敗→再試行、入力中の回転でも値とフォーカス復帰を維持する |

自動確認は、通常3サイズ（1280×900・1366×768・390×844）と320×568・667×375を、Desktop Chromium・Android相当Chromium・iPhone相当WebKitの3設定で行う。小さい2サイズでは長い内容と文字200%も含め、本体の実スクロール、最後の入力・操作、状態遷移を確認する。自動試験で可視領域を模擬しただけでは実キーボード合格としない。

Android Chrome通常/PWA、iOS Safari通常/ホーム画面PWAでは、両画面について実キーボード・日本語IME・縦横回転・上表の入力から末尾の確定/取消・閉鎖後の背景位置を確認する。入力への自動拡大とピンチ拡大を妨げず、キーボード表示中にもネイティブスクロールで到達できることを確認する。Windowsでは既存のTab/Shift+Tab/Enter/Escapeとブラウザ拡大の操作を維持する。

変更要否は次の順序で決める。

1. 変更前後とも対象条件に合格した画面は、変更不要のままとする。キーボード未実施の環境は保留とし、通常表示の合格で代用しない。
2. 変更後だけ失敗した場合は本対策の回帰として記録し、直近のCSS適用・補正の所有先・監視解除等を先に修正する。回帰を別の共通化で覆い隠さない。
3. 変更前から到達不能だった場合は既存不具合として記録し、当該画面だけを対象台帳へ追加する。まずネイティブスクロールでの到達を確認し、それでは足りない場合に、入力画面専用の外枠へ具体化2の補正と必要最小限の高さ制約を適用する。初回適用除外の例外は、この再現と根拠を記録した画面に限る。
4. 個別対策では通常時の幅と90vh上限を維持し、必要時だけ本体を専用外枠の内容領域以内にも制限する。高さの仕様は `max-height:min(90vh,100%)` を基本とし、割合の基準になる外枠には確定した高さを設ける。既存の余白を一度だけ差し引き、スクロール構造、ARIA/ref、保存処理、子確認とフォーカス復帰を維持して同じ条件を再確認する。最終的な外枠と上限値は対象台帳へ記録する。
5. これらの限定対策で解決できず、操作順・保存方法・固定領域・通常時の見た目を大きく変える必要が生じたときは、その変更を適用する前に、利用場面の例と選択肢を示してユーザーへ判断を求める。到達不能または実機未確認の条件は保留として残し、合格に含めない。

両画面の確認を理由に、回帰確認対象の全画面へ共通CSSやhookを一括適用しない。正式性能測定を毎回必須へ変えず、処理負荷と測定の扱いは下記の既存方針を維持する。

**動作を重くしないための制約と性能の扱い**

- スクロールはブラウザに任せ、通常の買い物や地図操作が行うDOM測定・React更新へ新処理を加えない。
- 新たな依存ライブラリ、常時のMutationObserver/ResizeObserver、全ダイアログ・全品目の継続走査を追加しない。入力ダイアログ表示中のviewport補正も対象外枠の数に比例する処理に限定する。
