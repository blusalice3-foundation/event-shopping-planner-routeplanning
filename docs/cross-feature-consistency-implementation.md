# 機能間の整合性：実装と移行手順

対象計画: cross-feature-consistency-remediation-plan.md（Q1〜Q3、I01〜I10、R1〜R39、P1）

## 保存と確認

- eventConsistencyを正式な保存先とし、イベント、日付、実在マップごとに所属・巡回順・訪問リスト・経路を保持する。簡易ホールと詳細ホールは保存元を含む参照で区別する。
- ブロック検出設定もIndexedDBへ保存する。旧localStorage値は移行時だけ読む。DB 8以降では移行前の退避確認で旧値を読まず、移行完了記録・アーカイブと保存データを検証した後は旧localStorage移行処理も実行しない。旧原本は保全し、削除は引き続き延期する。移行前の読み出し失敗や移行記録の破損は復旧対象にする。
- 操作は一つのキューで最新の保存内容から計算する。参照整理後も品目の並び順または実行列だけで完結する並び替えは、既存の約500msの監視保存で変更された一領域だけを保存する。訪問リスト・巡回設定・経路等の関連情報も変わる並び替えやその他の一括操作は、11領域、メタデータ、移行記録を同じトランザクションで確定する。監視保存も同じキュー内で完了を待ち、後続の計算・一括保存を先行させない。競合時は最大3回再計算し、一括操作の確定結果は保存成功後に画面へ反映する。
- 通常の購入状態・金額・数量・メモ等の編集は、書き込み失敗・abort・容量不足・継続する競合でも未保存の現在値として保全する。画面とJSON／Excel共通の出力用snapshotに保持し、再試行・退避・明示取消を選べる。保存済み基準・DBは成功するまで変更しない。保存後の画面反映失敗では再保存を案内せず、保存済み値からの再読み込みを求める。
- 利用マップの切替は、訪問リストの未確定変更・保存中の並び替えに対する遷移確認を先に処理する。確定または破棄が成功してから選択先を保存する。
- 確認待ちの間は他の操作を保存できる。確認対象・結果が変われば新しい確認を要求する。復元の置換では、削除される現在値も比較対象にする。
- 保存後の画面反映に失敗した場合は後続保存を止め、再読み込みを求める。保存済み内容を古い状態で巻き戻さない。

## 所属・巡回・編集

同じイベント・日付・マップで同じ番号セルを使う全品目は、候補列も含めて所属選択を共有する。境界上や競合する指定は利用者が選ぶまで確認待ちとなる。セルを特定できない場合は、正規化した同一スペースで共有する。A-01aとA-01bはこの場合別のスペースになる。

ブロック名は正規化後の完全一致を優先し、大文字・小文字だけが違う補完は候補が一つの場合に限る。同一ブロック内の重複番号は既存規則どおり行・列が小さいセルを選ぶ。その後、照合された別々のブロック間で同一座標をまとめ、異なる座標が残る場合は位置未解決とする。

品目編集は変更したフィールドだけを最新値へ適用する。日付・配置変更では、表示していないマップも含む影響を確認する。移動先の有効な選択を引き継ぎ、明示的な選択・自動判定への解除は移動先の共有単位全体へ適用する。

日付統合の確認画面では、統合先の日付表記、実行列の順序、最終的な表示モード、利用マップ、およびマップ別のホール巡回順・訪問品目順・経路順と設定を選択できる。順序は選んだ保存先を先にし、残りの品目・グループ・訪問リストも保持する。選択の変更は最新値から新しい確認案を作るだけで保存しない。再計算中は保存・取消を待機させ、古い確認で確定しない。確認後に元の対象や結果が変われば再確認し、統合で変更しない購入記録等の最新値を保持する。日付タブの長押しからの統合でも同じ選択を使い、選んだ最終モードを保存する。

確認済みの日付統合では、ホールIDの対応表を所属・ホール順・訪問リストへ一括適用し、legacyHallIdの旧形式表現も更新する。基本IDそのものと、解決済みグループに一致する既知の優先度接尾辞だけを対応付け、ID内のコロンや未知の接尾辞を推測で分割しない。通常のグループ解析も末尾の既知接尾辞だけを除去し、ホール順パネル・マップ表示・集計・巡回設定の分離と参照更新で共通の処理を使う。

ホール順の変更は各ホール内の最新の訪問順を保つ。保存後の取消基準は保存した順序になる。Undo・Redo・取消は現在の訪問単位の順序だけを扱い、追加された品目・訪問先の位置や購入記録を戻さない。イベント置換・改名・削除の成功時は古い編集・訪問履歴・遷移確認を終了する。

完了表示は実行列の重複しない品目集合をナビゲーターと共用する。候補品目は別バッジで表示する。日付タブの長押しは押した日付のモードを一度だけ切り替える。検索は品目IDと要求IDで対象を展開し、仮想リストの描画を待って移動する。

## 形式と読み込み互換性

| 層               | 現形式                                        | 読み込み                              |
| ---------------- | --------------------------------------------- | ------------------------------------- |
| IndexedDB        | DB 8、許容上限8                               | 旧DB 5〜7を移行。将来版は拒否         |
| 追加領域         | schemaVersion 1                               | 必須フィールド・参照・移行記録を検証  |
| JSONバックアップ | version 2                                     | version 1は全体構造を検証してから移行 |
| 完全版Excel      | formatVersion 3.0、consistencySchemaVersion 1 | 2.2以前を旧形式として読み込み         |
| XLSX Worker通信  | protocolVersion 2                             | 主スレッド・Worker双方で検証          |

JSONは実際にダウンロードする文字列を解析・検証してから、その同じ文字列を出力する。存在しない参照の整理は品目・購入記録を削除しない。型や構造が壊れた入力は、参照整理を行う前に拒否する。

### 完全版Excelの保持範囲

L＝配置、M＝マップ、R＝ホール定義・所属・巡回設定。完全版の品目とメタデータは常に出力する。

| 情報                                             | 必要な選択 |
| ------------------------------------------------ | ---------- |
| 実行列・日付別モード                             | L          |
| マップ・回転・表示位置・検出条件・利用マップ選択 | M          |
| 簡易ホール定義                                   | R          |
| 詳細ホール定義                                   | MとR       |
| マップなしの所属・全体巡回順                     | R          |
| マップ内の所属・全体巡回順                       | MとR       |
| マップなしの訪問品目                             | LとR       |
| マップ内の訪問品目・経路                         | LとMとR    |

未確定の旧設定は依存情報をそろえて出力する。省略した情報は空またはnullとし、contentManifestへ保持・省略件数と理由を記録する。簡易版では手動所属列を空にする。

既存の配置情報・マップデータ・ルート情報シートは維持する。新形式のルート情報シートはホール定義を扱い、新しい巡回情報は関連設定シートに置く。関連設定はUTF-16で30,000文字以内に分割し、サロゲートペアを分断しない。欠番・重複・未知バージョン・件数不一致・サイズ上限超過は拒否する。

## 更新前の退避

1. 旧版で「JSONバックアップ保存」を行う。旧版へ戻す可能性がある場合、この通常バックアップを必ず残す。
2. 新版の初回画面で「移行前データを保存」を押し、event-shopping-planner-pre-upgrade.jsonを保存する。
3. 旧版を含む他のタブを閉じ、「保存形式を更新して開く」を押す。確認中に元データが変わった場合は、更新された退避ファイルをもう一度保存する。
4. 移行後に品目数、購入記録、各日の実行列とマップを確認し、JSON version 2のバックアップも保存する。
5. 旧設定の確認欄に残る対応不明データは、表示された保存元と内容を確認してから対応先を選ぶ。日付統合も内容を確認して確定する。

DBの移行前アーカイブと完了記録はsyncQueueに保全する。更新中の失敗で一部だけを確定しない。記録と実データが矛盾する場合は通常保存を止め、既存の復旧経路へ渡す。

## 旧版へ戻す場合

更新後のDBを旧版へ開かせない。旧版941ebe7の実際のopenDatabase実装をテスト用に保存し、DB 8への読込・書込の拒否を確認している。

1. 元のブラウザープロファイルとDBを残し、別のプロファイルを作る。
2. そのプロファイルで旧版を開き、更新前に旧版で作った通常のJSONバックアップを復元する。
3. 品目数、購入記録、設定を照合してから旧版の利用を再開する。移行後に新版で行った操作は、更新前バックアップには含まれない。

移行前データファイルは全storeのキーと生の値、旧localStorage値を含む調査用アーカイブで、通常のJSONバックアップの入力形式とは異なる。通常バックアップがない場合は、元のDBとこのファイルを保全し、隔離した環境でアーカイブのdatabaseVersion・store構成・payloadを検証して復旧する。元の保存領域のDBバージョンを手動で下げたり、移行記録だけを削除して再移行させたりしない。
