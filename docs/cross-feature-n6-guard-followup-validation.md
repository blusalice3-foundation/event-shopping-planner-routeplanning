# N6 ガード情報欠落の追加修正・検証記録

作業日: 2026-10-15。開始時HEAD: `9325156cd6fb08a4a359c3735007047394f98f85`。

[追加整合性改善対策案](cross-feature-additional-consistency-remediation-proposal.md)の実装済み状態に対し、レビューで指摘された「`limitedPurchase` があっても `operationKind` と `guard` がないと対象検証を省略する」不足を補完した。

## 修正内容

- `requiresItemContentGuard` で、操作種別・ガード・限数入力意図のいずれかがある要求を識別する。`limitedPurchase` がある場合も有効なガードを必須とし、不足時は既存の再確認・適用除外へ戻す。
- 通常保存の計画と受理済み入力の表示・出力は、既存の共通ガード検証を通す。退避対象の収集とWorkerバックアップにも同じ識別関数を使い、全品目差分の再適用によって不足要求を復活させない。
- 通常のメモ・購入・数量編集、候補列の単品限数入力、フィールド競合、受理と保存の分離、操作順・まとめ保存を維持する。有効な単品ガードがあれば、操作種別を省略した要求も従来どおり処理できる。
- DB 11、共有品目payloadと変更イベントのsidecar、CAS、既存の日付コマンドを維持する。識別判定は定数時間で、追加のDB読取り・全体走査・保存キューは導入していない。

## 性能の確認

150 / 500 / 1,500品目 × 分散 / 集中配置 × 地図あり / なし × PC / スマートフォン幅の24条件を、修正後の製品ビルド・Chromium・1ワーカーで再測定した。1,500品目では全6操作について20サンプル以上、中央値50ms以下、95%点100ms以下の既存検査を維持する。

修正前との比較元は、同じ開始時HEADの[既存24条件の測定](../artifacts/shopping-operation-completion-n6-n8/performance-24-conditions.json)である。初回に超過した2条件は、独立作業ツリーで開始時HEADと修正後を同じ環境・データで続けて新規測定した。修正前24条件全体の新規測定は実施していない。保存完了時間は操作反応と分けて集計した。

確定した24条件は、初回通過22条件と追加測定の通過2条件の組合せである。1,500品目の8条件・全6操作で20サンプル以上を確保し、中央値の最大44.9ms、95%点の最大50.7msとなった。既存の50ms / 100ms基準を満たす。

初回は、1,500品目・集中配置・地図ありのPC幅で「戻る」中央値53.5ms、スマートフォン幅で「購入」51.8ms・「戻る」51.2msとなった。初回の失敗を含む[24条件の生結果](../artifacts/shopping-operation-completion-n6-guard-20261015/performance-initial-24-conditions.json)は保持した。追加測定では修正前後とも通過し、この超過は再現しなかった。製品コードは初回測定以降変更していない。

| 条件・操作           | 修正前      | 修正後      |
| -------------------- | ----------- | ----------- |
