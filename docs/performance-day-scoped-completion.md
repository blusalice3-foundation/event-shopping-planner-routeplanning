# 日付差分コマンドの追加実装とWindows実測

2026-10-10。このWindows端末の通常表示のChrome／Edgeで、最終ビルドの復元直後の初回操作と再操作の両方が暫定目標を満たした。キャッシュがない場合、別タブの保存でキャッシュが失効した場合、確認後の競合再試行でも、日付コマンドは対象イベントと対象日付のレコードを読み、変更した枝だけを保存する。

訪問先パネルの並び替え・取り消し・確定と、それらを伴う長押し変更の追加実装は[別記録](performance-visit-panel-day-scoped.md)を参照。以下の実測値はこの追加変更前のビルドに対する値であり、追加変更の再測定値ではない。

## 操作時の全体処理を削減

[日付レコード](../src/persistence/db/dayRecordStorage.ts)のイベント共通レコードに、子の日付キーとSHA-256を含む認証付き一覧を追加した。共通レコードの期待するハッシュは制御storeに保存する。[対象日付の読取](../src/persistence/db/scopedDayStorage.ts)は、全レコードのcursor走査や全イベントの品目・マップ取得を使わず、イベント共通情報と該当日付のペイロードを直接読む。小さな6ヘッダー、全11 storeのrevision・checkpoint、移行記録、保全記録、イベント世代も確認する。

dayModes、executeModeItems、hallDefinitions、hallRouteSettings、routeSettings、eventConsistencyが日付レコードを持つ。品目、イベント設定、回転、表示位置にはイベント単位の検証済み索引を、マップにはイベントごとの日付キー・ハッシュの一覧を追加した。品目は日付統合や所属確認に必要な対象イベントの一覧を読む。他イベントの品目は取得しない。

通常保存、差分保存、全体復元は、ペイロード・索引・期待ハッシュ・revision・checkpointを同じトランザクションで更新する。競合時は対象日付を読み直して最大3回再試行する。日付統合の確認と再確認はreadDay・commitDayで日付に限定する。保存失敗時の保留・取消・再試行、別タブの変更、削除・置換の操作世代、旧データの確認を維持する。

旧形式の変換と索引作成は、保存Workerの起動読取時に、画面操作を受け付ける前に一度行う。全体復元でも必要な形式を準備する。キャッシュが失効しても、この変換を日付操作内で再実行しない。全体起動読取、全体復元、構造変更、バックアップ、破損した保存内容の明示復旧は、各目的に必要な全量検査を行う。

実測対象ビルドのDBバージョンは10。認証付きの形式を更新できない9以前のクライアントを拒否する。旧保存内容の移行、外部JSONの検証、既存の全体取得・保存APIを維持する。未初期化・破損・ハッシュ不一致の対象レコードは自動採用しない。

画面が復元・保存結果を採用したとき、画面の保存済み状態とWorkerアダプターのキャッシュの参照を揃える。これにより、初回だけ発生していた過去10,000品目の深い比較も省く。Workerは保存した検証済み状態の参照を次の差分に使い、キャッシュ失効後の応答でも未変更のマップ全体を返さない。

## 計測条件

- Windows 11 Pro 10.0.26200、Ryzen 9 3900X、12コア／24論理プロセッサー、メモリー47.9GiB。Node 24.19.0、Playwright 1.62.1。
- インストール済みChrome 154.0.8037.99／Edge 154.0.4258.62を通常表示で起動。1280×900、ズーム100%、各テスト独立の保存領域。利用者のブラウザープロファイルやデータは変更していない。
- アクティブ500品目、40,000セル。過去なしと過去10,000品目（10イベント）を公開の復元UIから実復元し、IndexedDBの品目数・イベント数を確認した。
- 過去なし・ありをセッションごとに交互に配置（なし→あり、あり→なし、なし→あり）。全6方向を各30回×3セッション。各方向の最初の1回は分離し、再操作は87件ずつ集計。復元直後の初回の実行→編集は別に3件ずつ記録。中央値は中央値、p95はnearest-rank。
- アプリの時間計装・React profilerを使わない。実mouse.clickのDOMイベント時刻から、選択状態と一覧が更新されて2回のrequestAnimationFrameを経過するまでを表示完了の近似として測定。
- バックアップは罫線・色付き40,000セルに統一し、旧版と修正版で各3セッション、単独実行と並行入力を分けた。総時間は実clickからrunnerのdownloadイベント受信まで。並行入力は開始操作の40ms後に送出し、入力送出から対象行の表示と2フレームまで。
- 性能測定中にビルド・他のテストを同時実行していない。訪問先測定はWorkerメッセージを観測し、送信コマンドの種類も検査した。

旧版は8ae2d7c2ad093b2282e26b140aaf0267d56d1e5fのクリーンな別checkout。修正版はdd2ff879213e292c0140dad08aae5ad60f34d511に今回の未コミット変更を含めた本番形式のビルド。両ビルドのrelease identityとrelease-role.jsのSHA-256を生データに保存した。

## 回帰確認と再集計

単体・統合・Workerは220ファイル・2,391テストが成功。キャッシュなしで過去0件／10,000件を比較し、日付操作のcursor走査が0回、get("data")が小さな6ヘッダーだけで、過去イベントのキーを読まないことを検査した。通常保存による失効、確認後の日付統合、対象の改変拒否、旧形式マップの起動変換、応答の参照保持、失効後の応答サイズ、保存失敗・再試行、他タブ競合を含む。

機能面のブラウザー回帰は、検索ジャンプ、Tab、ドラッグ、印刷、スクロール保持、初期計測の範囲、集中セル、複数ホール、他タブ競合、日付統合、保存失敗・取消・再試行を含む129ケースが成功した。[各ケースとビルドの記録](performance-day-scoped-completion.regression.json)を保存した。DB 10に対応したXLSX公開操作・性能記録の検証スクリプトも関連32テストが成功した。

実測の生データと判定は[JSON記録](performance-day-scoped-completion.samples.json)。集計スクリプトは件数・セッション・ブラウザー・表示条件を検査し、中央値200ms・p95 300ms・過去増分30ms・単独バックアップLong Task 100ms未満・並行入力300ms未満を判定する。

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/summarize-day-scoped-performance.ps1
```

再測定は[ブラウザーテスト](../tests/browser/responsive-performance.spec.ts)を同じfixtureで実行する。サーバー起動後にPLAYWRIGHT_BASE_URLを設定し、PERFORMANCE_BROWSER_CHANNEL=chromeまたはmsedge、PERFORMANCE_HEADED=1を使用する。モードは --grep 'six mode transitions'、訪問先は --grep '@visit-performance'、バックアップは --grep '@backup-comparison'、いずれも --workers=1 --reporter=json。出力はPowerShellのSet-Content -Encoding utf8で保存する。旧版比較時だけPERFORMANCE_COMPARE_BASELINE=1を指定して旧版のURLを使用する。集計スクリプトの各report引数で保存先を指定できる。

型検査、ESLint、アーキテクチャ境界、テスト分類、DB互換性、文字コード、差分空白検査も成功。既存ファイルのencoding・BOM・改行を維持し、新規ファイルはUTF-8（BOMなし）・LF。代表文字列、U+FFFD、不自然な?、BOM、改行だけの差分を検査した。本番公開はしていない。
