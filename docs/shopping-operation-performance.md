# 実行・集中モードの品目操作と差分描画

購入変更・回答記録・限数の実購入数・一括操作は、最新の受け付け済み状態へ差分を反映する共通コマンドを使う。操作の受け付けと保存完了を分離し、次への移動では保存完了を待たない。

## 実装

- `useShoppingItemMutationCommands.updateItems` と `useApplicationSnapshot.updateItemFields` は、複数品目も一つの操作として受け付ける。操作番号と対象IDを保存キューで保持し、既存の数量正規化・保護レベル・競合判定を通す。
- `itemIndex` は品目IDの索引と変更位置を共有する。回答記録と移動時の検査は、この索引から最新状態を読む。変更履歴の親配列は弱参照で持ち、保存済みの配列を履歴として蓄積しない。
- `executionVisitIndex` は品目と訪問先の所属、訪問先順序を保持する。内容変更では対象訪問先の品目配列を更新し、購入済み件数・残額を差分で更新する。追加・削除・復元・所属や順序の変更では再構築する。
- 後回し・遅参のフェーズ開始時に固定するIDと一時表示の規則を維持する。変更されていない訪問先を再利用し、対象訪問先のフェーズ所属を再評価する。
- 実行モードのスペースとプレースホルダー、集中モードの品目をメモ化する。操作関数・ホール定義・未変更品目の参照を維持し、保存通知だけでカードの描画をやり直さない。描画関数はReactの確定済みpropsとして渡し、中断された並行描画の内容が保持行に混ざらないようにする。
- 画面外のカード操作部品を解放する。入力値は受け付け済み状態、展開状態は外部の行状態に保持する。フォーカス・編集・確認画面の対象を保持し、保存待ちだけでは保持しない。対応ブラウザでは、測定済みの高さを持つ非表示行のレイアウトを `content-visibility` で省略する。
- 実行モードの表示位置は、継続するDOM監視と表示範囲の候補から解決する。訪問先のID索引と対象行への直接検索を使い、次の訪問先一つを先読みする。移動と先読みが重なる間は保持要求を数える。
- 集中モードの地図は、経路用の入力と購入状態の入力を分離する。座標索引、ホール・経路設定、経路キー、背景・経路の描画を再利用する。Workerの応答は要求番号と経路条件を照合し、古い応答を棄却する。
- 「記録」の回答と実購入数は、通常メモの入力待機と分けて即保存キューへ入れる。内容が同じ記録でも待機中のメモを流す。保存通知の内容が同じ場合は品目参照を維持し、他タブの変更は該当品目へ反映する。

既存の差分通信、Workerによる全領域の整合性検査、保留、再試行を維持する。配列のコピーやReactの行照合まで完全な定数時間になる設計ではなく、全品目の再集計・全カードの描画・経路形状の再構築を品目操作から外す設計である。

## 計測

計測は初期状態で無効。開発者コンソールで有効にしてから操作する。

```js
window.__espShoppingPerformance.enable();
window.__espShoppingPerformance.reset();
// 購入、記録、移動などを操作する。
window.__espShoppingPerformance.read();
window.__espShoppingPerformance.enable(false);
```

`input` は共通コマンド・移動処理の受け付け時間、`paint` は次の描画機会までの時間、`save` は保存キュー投入からコミットまでの時間。直近500サンプルとコンポーネントの描画回数を保持する。品目の内容は記録しない。`paint` とブラウザ検証の反応時間は `requestAnimationFrame` と後続タスクを使った推定値であり、実機の入力遅延や画素表示完了そのものではない。

```powershell
npm run build:app
npx playwright test tests/browser/responsive-performance.spec.ts --workers=1 '--reporter=list,json'
```

JSONレポートの `shopping-operation-timings` 添付には、操作別の生サンプル、中央値、95%点、保存時間、描画回数を含む。必要なら `PLAYWRIGHT_JSON_OUTPUT_NAME` に出力先を指定する。`ESP_PROFILE_SHOPPING=1` を設定すると、実行モードのCPUプロファイルも添付する。

## 検証範囲

150・500・1,500品目、訪問先の分散と同一スペースへの集中、40,000地図セル、10,000履歴品目を使う。実行モードの全件閲覧後の連続購入、集中モードの購入・売切回答記録・記録直後の次への移動、地図の購入表示、数量・メモ入力、ズーム時の保持、編集対象の保持、スマートフォン幅をブラウザで確認する。

単体・結合テストでは、数量正規化、一括操作、限数の記録、戻る、フェーズの固定対象と切替、一時表示、連続操作の順序、未変更カードの描画停止、保存通知の参照維持、Workerの古い応答を確認する。保存Workerの書き込み失敗・再試行・再読み込みと、他タブの変更・競合の解決もブラウザで確認する。

スマートフォン実機は未検証。中央値50ms以下・95%点100ms以下は、この環境のブラウザ反応時間を使う暫定目標であり、保存完了時間には適用しない。

## 2026-10-08の計測結果

Windows 11、AMD Ryzen 9 3900X、メモリ約48GiB、Node 24.19.0 / npm 11.19.0、Playwright Chromiumの製品ビルドで測定した。ブラウザテストは1ワーカーで実行し、購入計測前に全品目のカードを一度表示したことを確認する。1,500品目の集中モードでは地図を表示し、150・500品目では非表示にした。

単位はms、各セルは中央値 / 95%点。実行モードの購入は各20回、集中モードの購入・状態変更は各21〜22回、分散配置の「次へ」は各21回。

| 品目数 | 配置         | 実行：購入  | 集中：購入・状態変更 | 集中：次へ  |
| ------ | ------------ | ----------- | -------------------- | ----------- |
| 150    | 訪問先に分散 | 14.7 / 21.2 | 13.5 / 14.7          | 12.0 / 13.5 |
| 150    | 同一スペース | 11.4 / 13.2 | 11.9 / 13.8          | 12.8（1回） |
| 500    | 訪問先に分散 | 24.0 / 32.1 | 12.8 / 14.8          | 12.9 / 15.0 |
| 500    | 同一スペース | 21.7 / 25.8 | 12.7 / 15.8          | 16.1（1回） |
| 1,500  | 訪問先に分散 | 54.8 / 68.5 | 26.4 / 34.5          | 30.0 / 34.9 |
| 1,500  | 同一スペース | 55.9 / 62.5 | 27.1 / 37.2          | 48.1（1回） |

1,500品目の実行モードは95%点100ms以下を満たすが、中央値50ms以下は最終測定で未達。集中モードの購入と、分散配置の次への移動は両方の暫定目標を満たした。「記録」は各条件1回だけの確認で、150〜1,500品目の範囲で9.2〜38.1ms。同一スペースの次への移動も1回だけなので、これらの中央値・95%点の達成を判断するサンプル数ではない。

購入コマンドの受け付け自体と保存完了は別に計測した。1,500品目では、実行モードの受け付けは両配置とも中央値0.1ms / 95%点0.2ms。保存完了は次の通りで、操作反応の目標には含めない。

| 1,500品目の配置 | 実行：保存    | 集中：保存    |
| --------------- | ------------- | ------------- |
| 訪問先に分散    | 109.2 / 125.2 | 104.1 / 127.6 |
| 同一スペース    | 112.5 / 137.1 | 108.1 / 164.1 |

実行モードの20回の購入中に記録されたカード描画は、1,500品目の分散配置で63回、同一スペースで58回。保持行の表示・先読み・保存通知による描画も含む。カード数はリスト上で60未満に抑えられることをブラウザで検証した。

単体・結合・Workerテストは216ファイル / 2,329件、ブラウザは16件が通過。型検査、変更したソースのlint、製品ビルドも通過した。保存失敗・再試行・再読み込み・他タブ競合の整合性検証は含むが、スマートフォン実機の検証は含まない。

生サンプル・描画回数・テストログは `artifacts/shopping-operation-performance-20261008/` に保存した。これはローカル計測結果であり、実機測定や既存のリリース承認の代替にはしない。
