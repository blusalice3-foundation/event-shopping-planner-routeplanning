# 追加監査N1〜N17の整合性改善実装

対象案: [cross-feature-additional-consistency-remediation-proposal.md](cross-feature-additional-consistency-remediation-proposal.md)
基準: `61ed939` / DB 11。2026-10-15実装。

## 変更内容

| 対象     | 実装                                                                                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| N1       | タイトル一致グループを先に照合し、シート由来の値で識別。残る対応は同じサークル・日付・ブロック・番号の組内だけで確認する。既存IDを二度使わず、未解決の対応がある場合は更新元も保存しない。                                           |
| N2・N4   | 初回取込と更新で全文CSV解析・列対応を共用。引用符内改行、カンマ、エスケープ、物理行番号を保持。URLはM列開始、旧CSVはA列開始。判別できないファイルは形式選択を要求する。解析失敗と0件を区別し、除外候補は確認する。                   |
| N3       | 取込用の行識別子をUUIDへ対応付けてから配置を適用する。重複除外した行の配置を別品目へ転用せず、一時情報を品目に保存しない。                                                                                                           |
| N5・N14  | 日付を空白正規化して対象を決定。全体配列の実位置へ挿入し、同日内ではブロック・番号だけを比較する。既存の手動順と日付原文を保持する。                                                                                                 |
| N6       | カード・一覧・集中の操作別に対象条件を捕捉。イベント世代、品目ID、日付、実行列、各品目の訪問先、選択マップ・正式な所属／訪問グループを受理済み表示・出力・保存時に再検証する。失効した限数入力だけを除外し、正常なメモ等を保持する。 |
| N7       | 予定数量の明示編集と未編集を区別。最新予定数量を保持し、実購入数の入力を失わずに同数・超過の確認をやり直す。                                                                                                                         |
| N8       | 非同期の取込結果を全呼出し元へ接続。保存完了まで入力を保持し、重複解決の完了・取消・失効を元の要求へ返す。保存開始後の取消で成功を取消扱いにしない。保存後のUI失敗・結果不明では再送を止め、古い要求の完了で新しい入力へ遷移しない。 |
| N9       | スマート挿入の単品・プレビュー・一括で共通の場所解決を使用。全角番号とASCII番号を同じ規則で解決し、実在する別ブロック定義を区別する。                                                                                                |
| N10      | 集中セッションのキーをイベント名・日付の組でエンコードし、所有イベントを完全一致で削除する。                                                                                                                                         |
| N11      | 編集フィールドごとの開始値を保持。明示的に開始値へ戻す編集も競合確認へ渡す。ガードが異なる操作をまとめず、同じバッチ内の入力順を保持する。                                                                                           |
| N12・N13 | XLSXの数式キャッシュ値・リッチテキスト等を共通に解釈。価格0と空欄を区別し、未知のオブジェクトは文字列化せず警告する。                                                                                                                |
| N15      | 大きな配列を関数引数へ展開する境界計算をループへ変更。描画セル・番号セル・結合セルの端点を直接扱う。                                                                                                                                 |
| N16      | 一覧と同じ日付照合で件数を集計。品目内容だけの変更では、既存の変更位置索引から件数マップを再利用する。                                                                                                                               |
| N17      | イベント名の読み出しは自身のプロパティだけを参照し、書込みは安全な共通処理を使用。作成・改名・復元・削除、設定、世代、入出力を含む。予約語による名前制限は追加しない。                                                               |

## 保存・互換性

- DB 11、JSON version 2、完全版Excel 3.0、XLSX Worker protocol 2を維持する。
- 一つの保存キュー、CAS、既存のイベント世代・確認token・再試行を使用する。
- 通常の購入・記録・集中モードの次へは、受理時に反映し、DB完了を待たせない。
- 限数入力は既存Workerの全snapshot読取・共有 `eventLists.data` 書戻し経路を使う。変更イベントのsidecarと保存制御情報以外を再保存しないことを検査する。厳密な日付限定品目I/Oへの変更は含まない。
- 既存の日付コマンドの品目変更禁止・限定I/O契約は維持する。
- 取込用の行識別子・要求ID、操作ガードは一時情報であり、外部JSON・Excel・永続品目へ追加しない。
- 誤継承済みの購入記録や失われた値を推測で修復しない。元データがある場合は既存の復元確認を使う。

### 製品ビルドの操作・保存性能

修正前の製品ビルドと修正後の製品ビルドを同じWindows環境、Node 24.19.0、Playwright Chromium、同じデータ、1ワーカーで比較した。150／500／1,500品目、配置の分散／集中、地図の表示／非表示、PC／スマートフォン幅の24条件を両方とも通過した。各条件には既存どおり40,000地図セル・10,000履歴品目を含む。

製品ビルド後に既存の `test:shopping-performance:run` を実行し24条件通過。npmの引数転送でJSONレポーター指定が欠けたため、数値の採取は同じビルドを次のCLIで直接起動して行い、再び24条件通過した（18.0分）。閾値・データ件数・サンプル数は変更していない。

```powershell
$env:PLAYWRIGHT_JSON_OUTPUT_FILE = "<出力先>/performance-after-report.json"
node node_modules/@playwright/test/cli.js test tests/browser/responsive-performance.spec.ts --grep '@shopping-performance' --workers=1 '--reporter=list,json'
```

単位はms。1,500品目の8条件（配置・地図表示・画面幅）について、各操作の中央値と95%点の最大値を示す。各条件・各操作20サンプル以上。

### 代表処理と保存I/Oの前後比較

基準コミットのソースと修正後ソースをメモリー内で別々に読み込み、同じNode 24.19.0・データ・TypeScript変換条件で比較した。各関数は3回のウォームアップ後に20サンプル測定。コンパイル時間を除く関数実行時間であり、ブラウザーの操作反応時間とは分ける。

単位はms、各セルは中央値 / 95%点。

| 処理                                   | 品目数 |              修正前 |        修正後 |
| -------------------------------------- | -----: | ------------------: | ------------: |
| 同名重複を含むシート照合               |    150 |         0.40 / 0.74 |   0.37 / 0.43 |
| 同名重複を含むシート照合               |  1,500 |         3.26 / 3.54 |   2.66 / 3.51 |
| 並び順を保った10件追加                 |    150 |         9.72 / 9.92 |   0.48 / 0.52 |
| 並び順を保った100件追加                |  1,500 | 1,045.59 / 1,104.17 | 54.20 / 54.82 |
| 連続限数100件の計画                    |    150 |         0.36 / 0.73 |   0.71 / 1.04 |
| 連続限数100件の計画                    |  1,500 |         0.36 / 0.72 |   1.12 / 1.20 |
| 限数100件＋メモ100件（限数50件が失効） |    150 |         0.54 / 0.65 |   0.64 / 0.90 |
| 限数100件＋メモ100件（限数50件が失効） |  1,500 |         0.83 / 0.90 |   0.74 / 1.16 |

有効な限数100件の計画ではガード検証の費用が増える。1,500品目での増分は中央値約0.76msで、通常の画面反応と保存完了は別途ブラウザー24条件で判定する。混在ケースの修正前は失効入力も適用してしまうため、処理結果の同等性を示す比較ではない。

Workerの品目保存は、過去品目0件／10,000件の両方で修正前後とも `get=99`、`put=6`、`openCursor=16`。既存の全snapshot読取を使い、ガードによる追加読取・書込はない。6件の書込先は対象イベントの品目sidecar、共有 `eventLists.data`、対象のroot digest、scope-ready、metadata、checkpointであり、別イベントのsidecarや日付設定・マップは書き込まない。通常のWorkerテストでも全snapshot読取1回と対象外の論理値の保持を検査した。

## 文字コード

既存ファイルのUTF-8、BOM有無、LF／CRLFを維持する。追加ファイルはUTF-8（BOMなし）・LF。提供された対策案は元のバイト列のまま保持する。

保存後に再読込みし、代表文字列「ユーザー登録」「エラーが発生しました」、U+FFFD、疑わしい疑問符、BOM、改行コードを確認した。提供案のSHA-256も元ファイルと照合し、一致した。
