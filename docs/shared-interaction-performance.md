# PC・スマートフォン共通のメモ入力・購入操作の軽量化

2026-10-07。150品目のメモ入力と購入状態変更を対象に、入力と保存の競合、入力ごとの保存負荷、一覧の描画負荷を改善した。スマートフォンの通常表示に加え、カードを保持するスペース別・ホール別の一覧にも共通処理の改善を適用している。

## 変更内容

- メモだけの連続入力は、最後の入力から300ms後にまとめて保存する。入力が続いても1秒以内に保存処理を開始する。フォーカス移動、ページの非表示、エクスポート、明示的な保存、別の変更操作では待機中の入力を保存キューへ渡す。購入状態・価格・数量は従来どおり待機時間を設けずキューへ渡す。
- 保存済みの状態と受け付けた入力を分ける。先行する保存が終わっても、後から入力したメモを古い値で上書きしない。表示とエクスポートに変更した項目の入力を反映し、保存失敗時には既存の再試行・競合検出を使う。
- メモ・価格・数量・購入状態だけの変更では、入力中の状態を対象品目の変更箇所から作る。地図を含む全データの比較を省き、変更していない品目や地図の参照を再利用する。構造変更や複数領域を同時に変える提案は従来の計画処理を使う。
- メモの一覧更新にはReactのtransitionを使い、カード内の入力を優先する。
- ブロックの配色と縞模様を品目の並びから決める。購入状態を変えても他の品目の背景色が連鎖して変わらない。同じ品目の並びであれば、購入済み・売切・後回し・限数への変更によって残り149品目の背景色は変わらない。購入状態を戻した品目は元の縞模様になる。品目の追加・削除・並べ替えでは再計算する。
- 80品目以上のカードを保持する一覧では、既存のネイティブ選択肢生成を使用する。価格・数量の選択肢と操作を維持し、Reactが保持する選択肢の要素を減らす。スマートフォンのスペース別・ホール別一覧も対象に含める。

## 同条件での比較

Windows 11、Playwright 1.62.1のheadless Chromium。PC配置1280×900、スマートフォン配置390×844、ズーム100%、150品目、100×100の地図、1イベント・1日・1ホール、実行モード、スペース別表示。独立したブラウザー保存領域に同じ検証用バックアップを公開UIから復元した。全品目をスクロールして表示した後の結果を掲載する。Android実機の計測ではない。

修正前→修正後を2回繰り返した。性能計測中にテストやビルドを並行実行していない。JavaScript処理時間は、各回10操作の前後でCDPのScriptDurationを取得し、20操作分の平均を求めた。操作の間隔は180msで、計測区間内の保存処理も含む。

| 条件                                                    |  修正前 |  修正後 |
| ------------------------------------------------------- | ------: | ------: |
| PC・メモ変更のJavaScript処理 / 操作平均                 |  33.6ms |  25.2ms |
| PC・購入状態変更のJavaScript処理 / 操作平均             |  55.8ms |  47.2ms |
| スマートフォン・メモ変更のJavaScript処理 / 操作平均     |  32.1ms |  24.8ms |
| スマートフォン・購入状態変更のJavaScript処理 / 操作平均 |  50.0ms |  44.4ms |
| PC・全件閲覧後のJSヒープ使用量                          | 20.06MB | 17.48MB |
| スマートフォン・全件閲覧後のJSヒープ使用量              | 18.95MB | 16.52MB |

JSヒープ使用量は、操作を行わず全件閲覧した別のブラウザー保存領域で、GCを実行してRuntime.getHeapUsageを取得した。1MBは100万バイト。ブラウザー全体のメモリ使用量を示す値ではない。

[計測サンプル・ビルド識別子・入力と保存の結果](shared-interaction-performance.samples.json) に、初期表示と全件閲覧後の値、フレーム待ちの各サンプル、保存確認を記録した。

## 応答時間と残る負荷

CPUの処理量は減ったが、2回目のrequestAnimationFrameまでの時間は計測ごとの揺れがあり、一律の短縮は確認できていない。この指標は画面が実際に発光するまでの時間やAndroid実機の体感を測るものではない。

カードを保持する表示方式では、全件閲覧後の150カード・18,300個のoption要素は残る。今回の選択肢の改善はReact側の要素を減らすもので、DOM自体を削減する変更ではない。多数のグループ見出しや一覧の集計・読み取りモデルの更新も引き続き負荷になる。

## 入力欠落と保存の確認

修正前は、地図あり・スペース別・150品目で、末尾へ20文字を40ms間隔で入力すると、PC配置とスマートフォン配置で入力と保存から文字が欠落した。修正後は同条件の連続入力と、100ms間隔、地図なしの通常一覧を含む6条件で、20文字すべてが入力後と再読込後に残った。各ブラウザーのページエラーは0件だった。

## 再計測

PowerShellでAGENTS.mdのUTF-8コンソールラッパーを適用し、アプリを起動する。

```powershell
npm run build:app
node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 4189
```

別のPowerShellで公開UIを使う計測を実行する。既存の利用者データを使わず、新しい独立したブラウザー保存領域で検証する。

```powershell
node scripts/performance/responsiveInteractionLatency.mjs http://127.0.0.1:4189
```

LAG_CASES環境変数で条件を指定できる。各条件はlayout（pc / smartphone）、count、mode（execute / edit）、grouped、mapCellsを持つ。typingOnly=trueは末尾への20文字入力と再読込後の保存だけを検証し、typingDelayで入力間隔を指定する。memoryOnly=trueは全件閲覧後のGCとJSヒープの計測だけを行う。

修正前は80ff9da20439b845553758acccaf95effd2de1daの別のチェックアウトからビルドした。修正後は未コミットのソースからビルドしたため、同じsourceShaでもバンドルのSHA-256が異なる。この記録はローカルの診断であり、リリース承認用の性能証跡には使用しない。
