**アイテム更新確認：9件の不具合・仕様不整合への詳細修正プラン**

作成日：2026-10-18（日本時間）  
対象：アイテム更新確認と、その取得・照合・保存・再試行に関係する処理  
基準コミット：`f15552d`  
改訂日：2026-10-18（日本時間）

状態：実装前。基準コミットの既存コードと照合し、正規化衝突時の優先順位、hook外の終了経路、表示要求拒否の範囲を改訂。実装・実装後の性能達成は未検証。

この計画の目的は、**確認済み9件を修正しながら、自動照合による更新の簡便さ、購入記録の保護、既存の操作速度を維持すること**です。更新要求の管理、更新元の判定、品目の照合という三つの境界を整理し、修正同士が矛盾しない構成にします。

確定仕様は次のとおりです。

- 品目ごとの選択を設けず、自動照合と一括確認を継続する。
- 購入済み品目の数量変更は、実購入数・支出集計も変わることを明示して一括同意する。
- 完全重複行は更新でも新規追加しない。既存の別IDは自動統合しない。
- 現行の文字列照合で成立する対応を先に固定し、空白除去後の照合は未対応分の救済に限定する。改題と正規化衝突が重なっても、現行の既存ID対応を再配分しない。
- 現在の保存形式、購入状態、価格・メモの保持規則、保護設定、競合確認、日付統合確認を利用する。
- 通常運用は単一PWA画面とし、同一画面内の入力変更・保存待ち・再試行を検証する。

9件の対応関係を、実装・テストで共通して使う番号に固定します。

| ID  | 問題                                     | 修正後の状態                                     |
| --- | ---------------------------------------- | ------------------------------------------------ |
| 1   | 前後空白による削除・新規追加             | 比較時の前後空白だけで既存IDを失わない           |
| 2   | 先行する未保存操作への再読込案内         | 確認を保持し、先行操作の再試行・取消へ案内する   |
| 3   | 入力変更後も旧イベントを更新できる       | 無効になった入力からの取得・確定を停止する       |
| 4   | 実購入数維持という誤説明                 | 数量変更と購入数・支出集計の関係を正しく説明する |
| 5   | 空欄でも旧シート名を送信する             | 表示された入力値どおりに取得する                 |
| 6   | 異なるgidでも更新元が古いまま残る        | 実際に使用した更新元を品目と一緒に保存する       |
| 7   | 未変更CSVの更新で重複品目が増える        | 同じデータの反復更新で追加件数・予定額が増えない |
| 8   | 保存保留後のチェックと再試行内容の不一致 | 保存中の表示と、再試行する提出内容を一致させる   |
| 9   | 古い取得が後続取込を終了させる           | 各要求が自分の結果だけを一度通知する             |

実装は、以下の順序で進める設計です。

1. **修正前の基準と回帰テストを確保する**

   最初に9件の再現条件を、正常な期待結果を検証する恒久テストへ置き換えます。以前の一時テストにある「誤動作すること」の検証を、そのまま成功条件にはしません。

   通常更新、同じ更新元からの再取込、更新元切替の三つの入口について、ID・件数・購入記録・更新元・実行列の基準データを用意します。修正単位ごとに、不具合の解消と既存正常系の両方を確認します。

   ファイル修正前にはgit状態と文字コード・BOM・改行を確認し、保存後には再読込と差分確認を行います。前回の一時検証物が残る作業ツリーは、最終品質検査には使用しません。

   レビュー報告にある既存テスト9ファイル・146件の通過は、修正前の基準情報として扱います。今回追加する回帰ケースや、修正後の通過を示すものにはしません。実装着手時と完了時に、対象ファイル・件数・コマンド・コミット・結果を記録します。

2. **更新要求の所有権と状態管理を統一する――ID 2・3・8・9**

   主な対象は[更新コマンド](../src/app/commands/useEventUpdateCommands.ts)、[取込・重複選択の作成元](../src/app/commands/useShoppingItemMutationCommands.ts)、[Appの無効化処理](../src/App.tsx)、[画面との結線](../src/features/app-shell/components/AppOverlayLayer.tsx)、[モーダル制御](../src/app/state/useAppOverlayController.ts)です。hook内だけの修正で完了とはしません。

   更新要求ごとに、操作ID（`updateOperationId`）、取得世代、対象イベント、入力の有効性を調べる関数、確認元の品目、更新元、要求作成時に捕捉した完了通知先、処理状態、通知済みフラグ、所有する表示要求IDを保持します。通常更新・同一更新元からの再取込・更新元切替で同じ管理を使います。取込元のuseShoppingItemMutationCommandsで重複選択を開く前に操作を登録し、通知先・入力の有効性を捕捉します。選択後の更新・別名作成・固定追加・取消にも同じ所有情報を引き継ぎ、それぞれ既存の処理結果で一度だけ完了させます。Appの無効化処理は表示中のpending状態だけに依存せず、取得中・URL待ち・選択待ちも含めて対象イベントから所有操作を特定します。

   **操作ID・取得世代・モーダルrequestIdを分けます。** 操作IDは更新全体、取得世代は各取得、requestIdはURL入力・更新確認それぞれの表示要求を識別します。保存処理の`application.confirmations`にある`token.operationId`は別のIDであり、更新操作IDとして流用しません。URL再入力や再取得は同じ操作と完了通知先を引き継ぎ、取得世代だけを進めます。同じ操作の古い応答は無視し、進行中の再取得を終了させません。

   終端処理は操作IDを明示する共通関数（例：`finishUpdateOperation(updateOperationId, result)`）に集約します。終了済みの操作への再呼出しは何もしません。終端状態・通知済みフラグをcallbackより先に確定し、その操作が捕捉した完了通知先だけを一度呼び、取込元が待つPromiseを完了させます。後から共有refを探して通知先を選びません。画面を閉じる処理、一覧への復帰、比較元・保存中表示の解除は、現在の操作IDと所有するrequestIdが一致するときだけ行います。

   hook外の既存経路も、次のとおり共通関数へ接続します。App側の現在の直接callback呼出しや、URL画面を閉じるだけの処理を残しません。

   | 既存経路                                                                                                                                            | 改訂後の結線                                                                                                                       |
   | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
   | Appの`application.handlers.current.applied`にある`pendingDuplicateEvent.complete`／`pendingEventUpdate.onImportComplete`の直接無効化通知と画面close | 対象に対応する操作IDを渡し、共通の`invalidated`終了へ委譲。URL入力待ちも同じ所有情報で終了する                                     |
   | 削除・改名成功時に呼ぶAppの`closeEventUpdateForEvent`                                                                                               | 対象イベントに属する操作だけを共通の`invalidated`終了へ委譲。`applied`側と重なっても通知は一度                                     |
   | AppOverlayLayerのURL入力`onCancel`                                                                                                                  | 所有操作ID付きの取消handlerへ委譲し、`cancelled`通知・Promise完了・所有画面close・既存の一覧復帰を一つの経路で行う                 |
   | hook内の確認取消、入力無効化、終端失敗、保存結果、表示要求の拒否、後続操作への置換                                                                  | 同じ共通関数へ委譲。取得中・URL入力待ち・確認中の旧操作だけを`invalidated`で一度終了させ、その後の遅着応答は通知・画面操作をしない |

   取得失敗後にURL再入力を提供し、表示要求が受理された場合は、同じ操作の「URL入力待ち」へ遷移します。現行の`onError`からURLを開いた直後に`failed`を通知する経路を分岐し、この場合は未完了のまま通知先を保持します。再入力を提供せず終了する失敗だけを`failed`とし、URL表示要求が拒否された場合は当該操作を`invalidated`で終了します。

   入力の有効性は、重複イベント選択時だけでなく、取得結果の受理前、確定開始時、既存の保存ガードによる再計画・再試行時にも検査します。入力変更や画面離脱は、この境界で検知します。検知のためのポーリングは追加しません。

   保存中の操作制限は、この要求状態から導出します。数量チェック・二重確定・更新確認そのものの取消を固定し、保存保留中も同じ提出内容を表示します。既存の保存再試行・取消バナー、実際の競合確認、日付統合確認は操作可能にします。保存試行が取消・失敗で確認中へ戻った後に、数量チェックを再び変更可能にします。保存中・CAS保留中は新たな更新開始を入口で受け付けず、既存の保存・再試行・保存試行取消へ案内します。旧操作を置換・終了してから保存結果を待つ構成にはしません。拒否した新要求側に完了待ちがある場合は、その要求だけを`invalidated`で完了させ、保存中の操作と通知先には触れません。通常の買い物入力は、既存の保存ガードに従って継続可能とします。

   **別ダイアログの優先による終了は、更新確認・URL入力の表示要求が拒否された場合に限定します。** 表示用portは既存controllerのrequestIdを呼出元へ返し、更新操作に関連付けます。requestIdが生成されたことだけを表示成功とは扱いません。controllerの同じ純粋な状態遷移で、当該requestIdの受理・拒否の受付結果を記録し、コミット後に操作ID付きの待ち先へ返します。既存のbusy／stale要求を反映しない規則は維持します。一時的な描画前の不一致、同一バッチ中のclose／open、別要求への遷移だけを拒否と判定しません。受付結果は更新確認・URL入力の要求に限定し、消費・終了後に解放します。

   受付結果の実装はcontroller内の局所キューとします。各open actionを既存reducerへ一度適用した直後のevent種別・requestIdで、その要求の受理・拒否を純粋に記録します。公開のoverlay状態・既存reducerの規則は維持します。任意の受付callbackをdispatch前にrequestId別Mapへ登録し、コミット後のeffectでMapから削除してから一度返します。消費済みIDだけをキューから除去し、同時に追加された結果を消しません。callbackは操作ID・取得世代・requestIdを捕捉し、受信時にも同じ表示要求の待機中であることを確認します。StrictModeのeffect再実行や古い受付結果による二重終了を防ぎ、画面離脱時の終了も共通処理に集約します。

   保存中の競合確認・日付統合確認は、Appの`application.confirmations`による別管理です。これらが表示されても更新操作を終了させず、保存中状態と提出内容を維持します。その確認や保留保存の取消は保存試行だけを戻す操作とし、更新全体の完了通知を行いません。受理済みの更新確認がこれらに覆われたことも、表示要求の拒否に含めません。

3. **更新元の入力・取得・保存を一致させる――ID 5・6**

   対象は[更新元判定](../src/features/events/duplicateEvent.ts)と[URL入力画面](../src/components/UrlUpdateDialog.tsx)です。

   保存済みシート名は入力欄の初期値として表示します。利用者が空欄にした場合は、本当に未指定として送信します。「名前指定は名称を優先、空欄はURLのgid、gidもなければ先頭シート」という扱いを画面でも説明します。

   同一更新元の判定は、実取得の優先順位と揃えます。

   | 指定内容                                | 判定方針                                   |
   | --------------------------------------- | ------------------------------------------ |
   | 両方にシート名がある                    | 既存の名称優先による判定を維持             |
   | 両方とも名称なし・gidあり               | 正規化したgidも比較                        |
   | 両方とも名称・gidなし                   | 同じドキュメントの先頭シート指定として扱う |
   | 片方だけ名称あり、またはgidの対応が不明 | 同一と断定せず、更新元切替へ進む           |
   | ドキュメントが異なる                    | 更新元切替へ進む                           |

   確認に使ったURL・シート名を、そのまま保存対象にします。品目だけ先に更新して更新元を残す保存は行わず、品目・更新元・実行列を既存の一括保存で確定します。追加のシート照会APIは設けません。

4. **更新専用の空白照合を追加する――ID 1**

   対象は[照合処理](../src/features/events/sheetMatching.ts)です。

   **現行の照合で成立する対応の維持を、正規化後のタイトル一致より優先します。** 空白除去は既存照合への追加救済とし、全入力について次の順に照合します。
   - ①元の文字列によるタイトル込み一致
   - ②元の文字列によるタイトル以外の一致
   - ③前後空白を除いたタイトル込み一致
   - ④前後空白を除いたタイトル以外の一致

   ①②は現行と同じキー・同じ照合規則で全グループの処理を完了し、その対応を固定します。③④は①②で未対応の既存ID・入力行だけを対象にします。各段階を全体で完了してから次へ進め、グループごとに四段階を完結させません。正規化後に似たタイトルが見つかっても、確定済みの対応を組み替えません。したがって、改題時の現行の由来値優先・順序対応も③④より優先します。

   正規化は比較値の前後空白に限定します。内部空白の圧縮、全角半角の一括変換、番号の数値化は行いません。元配列を正規化して書き換えず、比較用キーだけを作成します。保存済みの日付・サークル・配置を直接書き換えず、共有の配置キーも維持します。

   各段階で現行のグループ照合を再利用します。グループ内の由来確認条件、一意なシート価格・シート備考の組合せによる優先対応、残余の既存品目順・入力行順での対応、IDと入力行を一度だけ使う規則を維持します。由来不明の値を新たに信頼して優先対応させる変更は加えません。

   正規化衝突と改題が重なる次の例を、恒久的な回帰テストへ追加します。他の識別欄は同一、価格は確認済みのシート由来値とします。

   | データ | サークル | タイトル | シート価格 |
   | ------ | -------- | -------- | ---------: |
   | 既存A  | `"X "`   | 旧A      |        500 |
   | 既存B  | `"X"`    | 旧B      |        700 |
   | 入力0  | `"X"`    | 旧A      |        700 |
   | 入力1  | `"X"`    | 新A      |        500 |

   期待値は**入力0→B、入力1→A、追加0件・削除0件**です。②で現行どおり入力0→Bを固定し、④で残った入力1→Aを対応させます。適用後はAのタイトルが「新A」、Bが「旧A」となり、各IDの購入状態・購入記録・利用者価格・利用者メモ・実行列の参照は別IDへ移りません。Aのサークル名`"X "`など既存識別欄の保存値も維持します。数量・価格・メモの適用は既存の同意・保持規則に従い、この対応付け変更で規則を変えません。

   上記の再取込、入力順を入れ替えた場合、由来値が不明な場合の現行順序対応も検証します。特に、現行①②で全件対応する入力では修正前と同じ対応になることを固定し、通常更新・同一更新元の再取込・更新元切替でも差分作成と適用結果が一致することを確認します。

5. **照合後の追加候補だけ重複除外する――ID 7**

   対象は[差分作成](../src/features/events/updateDiff.ts)です。処理順を以下に固定します。

   **CSV解析・必須項目除外 → 既存のURL補完 → 重複キー用の数量評価 → 照合 → 対応済み行のキー登録 → 未対応行の検証・重複除外・追加**

   照合前の入力全体や、既存品目配列をまとめて重複除外する方法は採りません。既存の別IDと個別の購入記録を保持するためです。

   重複キーには既存の完全重複判定を利用します。ただし、CSV解析直後の仮の数量1を使わず、`rawQuantity`を既存の数量判定で評価した値を使います。この数量投影は比較専用とし、元の入力値を上書きしません。

   空欄は重複キーでは新規取込時と同じ数量1として扱い、既存品目への適用では現在数量を維持します。不正数量行は重複判定用Setへ登録せず、後続の有効行を巻き込まないようにします。

   | 既存ID数 | 同じ完全重複入力 | 結果                           |
   | -------: | ---------------: | ------------------------------ |
   |      0件 |              2行 | 新規1件                        |
   |      1件 |              2行 | 既存1件を維持                  |
   |      2件 |              2行 | 両方のID・購入記録を維持       |
   |      2件 |              1行 | 従来の削除確認・保護規則を適用 |

   表示する重複除外件数は「入力内の重複総数」ではなく、**新規追加を抑止した行数**と定義します。取込対象、数量不正による新規除外、重複による追加除外、必須項目不足を区別し、件数と実際の更新結果を一致させます。

6. **確認画面と説明を実際の動作へ合わせる――ID 4および全体の表示**

   対象は[更新確認画面](../src/components/UpdateConfirmationModal.tsx)、Appからの受渡し、READMEです。

   対象イベント名を通常更新・更新元切替の両方に表示します。保存中表示と操作可否は更新要求の状態から受け取り、モーダル独自の送信状態を別に持たせません。

   数量説明は次の二つを区別します。
   - 購入済み：数量変更は実購入数と支出集計にも反映される。
   - 限数購入：予定数量を変更し、実購入数は維持する。

   混在していても一括チェックは一つとし、既定OFF、確認内容変更時の同意解除、最大5例の表示を維持します。価格の入力値と利用者メモは現在値を保持します。

   重複除外は同じ確認画面内に件数を表示し、新しい確認操作を増やしません。

保存・取消・通知の扱いは、全入口で次に統一します。特に、**保存試行の取消と、更新確認全体の取消を混同しないこと**を実装条件にします。

| 契機                                         | 次の状態                         | 取込全体の完了通知                |
| -------------------------------------------- | -------------------------------- | --------------------------------- |
| 有効な取得結果を受理                         | 確認中                           | しない                            |
| URL再入力へ移動／取得失敗から再入力を受理    | 同じ操作でURL入力待ち            | しない                            |
| 更新を確定                                   | 保存中                           | しない                            |
| CAS競合などで保存Promiseが保留               | 保存中を維持                     | しない                            |
| 先行未保存操作、Abort、Quotaなどで確認を保持 | 編集可能な確認中へ戻る           | しない                            |
| バナーで保留保存を取消、追加確認を取消       | 確認中へ戻り、再確定を必要とする | しない                            |
| 更新確認・URL入力そのものを取消              | 終了                             | `cancelled`を一度通知             |
| 入力・対象イベント・確認元が無効化           | 保存せず終了                     | `invalidated`を一度通知           |
| 更新確認・URL入力の表示要求を拒否            | 当該操作だけ終了                 | `invalidated`を一度通知           |
| 取得中・URL待ち・確認中に後続操作で置換      | 旧操作だけ終了                   | 旧通知先へ`invalidated`を一度通知 |
| 保存中の競合確認・日付統合確認を表示         | 保存中を維持                     | しない                            |
| 再入力を提供しない取得失敗                   | 終了                             | `failed`を一度通知                |
| 同じ操作の古い取得結果／終了済み操作の応答   | 現在の操作・世代に影響しない     | しない                            |
| 保存・画面反映が成功                         | 終了                             | `saved`を一度通知                 |
| 保存結果不明／保存後の画面反映失敗           | 終了                             | 既存の専用結果と案内を一度通知    |

保存成功後に入力が変わっても、結果を無効へ書き換えません。入力世代が変わった場合は、新しいフォーム入力の消去だけを抑止します。また、`finally`で無条件に確認状態へ戻したり、別要求の保存中表示を解除したりしないようにします。

性能面では、照合と追加重複判定をMap／Setによる固定回数の走査とし、追加処理の時間・領域を **O（既存件数＋取込件数）** に抑えます。①②の既存処理を終えてから、残余だけの③④を固定回数で処理します。各段階につきグループを一度構築し、入力行ごとの全件検索・グループ再構築は加えません。要求の所有権・世代確認は原則O（1）とします。数量チェックの操作や状態表示だけで再照合、deep clone、再取得、追加保存が走らない構成にします。モーダルの受付結果も要求ごとに消費し、通常の買い物操作へ全件走査や追加の保存処理を持ち込みません。

更新処理は150／500品目の同じ入力で修正前後を比較し、取得待ち・照合／差分作成・確認表示・数量チェック・保存完了を分けて記録します。通常更新だけでなく、正規化衝突・改題・完全重複を含む入力も使います。共有App経路への影響については、指定の買い物性能基準を適用し、各条件・各操作を個別に判定します。条件間の平均で遅い操作を隠しません。

- 150／500品目、全16条件、各6操作
- 各操作20サンプル以上
- 中央値55.0ms以下、95%点100ms以下
- 保存完了時間は操作反応時間と分けて記録
- 過去の50ms基準の記録と当初の合否を改変せず、新基準の判定を区別して記録

既存の`tests/browser/responsive-performance.spec.ts`と`npm run test:shopping-performance`は、1,500品目の追加8条件も実行します。上記150／500品目・16条件を必須範囲として維持し、既存の1,500品目測定も削除・緩和しません。測定は既存の1 worker設定で行い、診断用プロファイルの結果を合否用へ混ぜません。設計上の計算量だけで達成とせず、同じ測定環境での修正前後の結果、各操作のサンプル数・中央値・95%点、保存完了時間を成果物へ残します。未達なら共有App経路や再計算の増加を調べ、基準を変更せずに改善して再測定します。

最終的な完了条件は、9件の回帰テスト、既存正常系、保存・再読込、性能測定が通過し、クリーンな環境で文字コード・書式・型・品質検査が成功することです。

文字コードは各既存ファイルのencoding・BOM・改行を維持し、保存後に再読込します。U+FFFD、不自然な疑問符の増加、意図しないBOM変更、改行だけの大量差分を異常として扱い、日本語の代表文字列「ユーザー登録」「エラーが発生しました」の破損も検査します。

そのうえで、**同じコミットに対するfoundation-qualityとrelease-a-rollbackの両方の成功**を確認します。既存の検査条件や性能基準を緩めて通過させることはしません。
