# 高速化変更の前後比較

変更前 `058a9b9` と変更後 `e9ceb0e` の本番向けビルドを同じ環境で比較した。以下は各条件3回の中央値。各版・各品目数につき予備実行1回を除外し、計24回（集計対象18回）を実行した。両ビルドのソース状態はclean。

測定開始: 2026-10-08 13:23:53 JST（04:23:53 UTC）。Microsoft Windows 11 Pro、AMD Ryzen 9 3900X 12-Core Processor、メモリ47.9GiB、Node 24.19.0、Playwright Chromium 151.0.7922.34、1280×720。CPU制限なし。毎回新しいブラウザコンテキストを使い、Service Workerは両版とも無効。150・500・1,500品目に、4万セルの地図と過去イベント1万品目を含めた。測定順は前→後、後→前、前→後と交互にした。

1,500品目では、全件閲覧後のメモ入力の反応が73.7%、検索が81.5%、拡大が72.2%、集中モード開始が66.8%短縮した。全件閲覧後のカードは1,500→4、optionは183,000→488へ減った。

初期画面の数量変更と連続購入は、保存完了がそれぞれ57.0%・45.3%短縮したが、反応指標は17.2%・40.0%増加した。すべての入力反応を改善できた結果ではない。ピンチの最大フレーム間隔の中央値は18.0→17.7ms、完了は389.4→397.4msで、この条件では大きな改善を確認できない。

## 測定方法

「反応」はDOMに入力を渡してから2回目のrequestAnimationFrameまでの時間で、描画フレームを使う反応の代理指標。集中モードを開く操作では操作ボタンが現れてから2フレームまで、ピンチでは最初の入力から次のフレームまでを反応として記録した。OSや物理ディスプレイまで含む遅延ではない。

「完了」は数量・メモ・購入状態がIndexedDBの値と一致した時点。保存確認は反応の測定後に、同じ接続で読み、20ms間隔で再検査する。メモの既存の約300msの待機時間を含む。購入直後の移動では次の訪問先の表示と購入の保存を確認した。検索は対象カードの表示とスクロールの安定まで、集中モードは経路Workerの応答と次の2フレームまで、地図は経路要求が残っておらず画像が60ms間隔で3回安定するまで。拡大と編集ダイアログの完了は反応と同じフレーム時点。確認処理の時間も含むため、トランザクション自体の所要時間ではない。

購入は3品目を同じタスク内でクリックし、数量・メモ・日本語検索は同一のDOMイベントを両版へ送った。ピンチは10フレームに各3入力、計30入力。全件閲覧は4行ごとにスクロールし、不足があれば追加で訪問する。全品目のカードが生成されたことを確認して先頭へ戻した。自動スクロールには測定用の処理が含まれるため、閲覧所要時間は速度の集計対象に含めない。

短縮率は（変更前−変更後）÷変更前。負の値は中央値が増えたことを示す。少ない標本で統計的な有意差を判定していないため、小さな差はばらつきと合わせて読む。

## メインスレッドの長い処理

1,500品目の操作開始から完了までに検出した、50ms以上のLongTaskの最大時間。各操作3回の中央値。0は50ms以上の処理が検出されなかったことを示し、処理自体がなくなった意味ではない。

| 操作                 | 変更前(ms) | 変更後(ms) |
| -------------------- | ---------: | ---------: |
| 数量変更（閲覧前）   |         94 |          0 |
| 連続購入（3品目）    |         93 |          0 |
| 全件閲覧後のメモ入力 |         92 |          0 |
| 地図表示中の数量変更 |         81 |          0 |

変更後の初期数量変更では3回中1回に64msのLongTaskがあった。他の上記操作では変更後の3回とも50ms以上のLongTaskがなかった。描画フレームの待ち時間とLongTaskは別の指標であり、停止時間の減少と反応指標の悪化の両方を記録した。反応が増えた原因は、この測定では切り分けていない。

## 入力と保存結果

全24回で、変更した数量・メモ・4品目の購入状態・地図表示中の数量が保存結果と一致し、再読込後も一致した。ページ内の未処理エラーは0件。この比較実行では保存失敗や他タブ競合を新たに起こしていない。それらの動作検証は既存のブラウザテストに含まれる。

## 記録と再実行

[集計JSON](summary.json)に中央値と全条件の最小・最大、フレーム間隔、50ms以上のメインスレッド処理の記録を保存した。[生ログ](raw.jsonl)のcase行からwarmup=falseの行だけを集計している。[共通測定スクリプト](compare.mjs)を両版に適用した。

同じ依存パッケージを持つ058a9b9とe9ceb0eの分離したチェックアウトで、それぞれnpm run build:appを実行し、Vite previewを127.0.0.1:4271（前）と4272（後）で起動する。依存パッケージのjunctionはリリースのモジュール境界検査で拒否されるため、この測定では同じnode_modulesを各チェックアウトに物理コピーした。スクリプトのPlaywright importは今回のワークスペースを参照する。

```powershell
$env:BENCH_COUNTS = '[150,500,1500]'
$env:BENCH_ROUNDS = '3'
$env:BENCH_WARMUPS = '1'
node artifacts/performance-comparison-20261008/compare.mjs
```

これは同一PC上の合成データによる測定で、実際のイベント地図・端末・入力機器による差は未測定。6点をまとめて変更したため、速度差を各変更単独の効果として分離していない。
