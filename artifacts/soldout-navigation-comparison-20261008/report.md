# 売切の確認画面と次の訪問先への移動：変更前後の比較

一部は改善しましたが、この操作全体の遅さが解消したとは言えません。1,500品目では、集中モードの確認画面表示は速くなった一方、実行モードの確認画面表示と、両モードで回答を「記録」した際の反応には悪化が見られました。

変更前 `058a9b9` と変更後 `e9ceb0e` の、クリーンなソースから作成した本番ビルドを同じPCで比較しました。今回の測定に伴うアプリのソース変更はありません。

## 条件と操作

- Windows 11、Ryzen 9 3900X、RAM約48 GiB、Chromium 151.0.7922.34（headless）、1280×720、CPU制限なし。スマートフォン実機は未測定です。
- 150・500・1,500品目。地図40,000セル、過去10イベント合計10,000品目を含む同じバックアップを復元。表示倍率100%、PCレイアウト。初期表示付近の訪問先を測定しました。
- 各品目のサークル・スペースは異なります。状態が「購入済」の品目を「売切」に変更し、確認画面で「通販･別イベ頒布無」を選んで「記録」。画面が閉じた直後に次へ進み、保存完了まで待ってから次の測定を行いました。
- 実行モードは「スペースを閉じて次のスペースを展開」、集中モードは「次の訪問先」を使用。実行モードのスペース一覧ナビゲーターによるスクロールや、自動移動は測っていません。
- 各バージョン・品目数・モードにつき独立したブラウザーコンテキストを使用。最初の1訪問をウォームアップとして除外し、続く3訪問を測定。中央値は同じコンテキストの連続3訪問であり、独立した3回の起動測定ではありません。
- 各18ケースで、対象品目IDと次のサークルの表示、売切状態と回答のIndexedDB保存、再読込後の一致を確認。ページ例外は0件でした。

## 測定の限界と再現

DOMとrequestAnimationFrameを用いた反応の近似測定であり、OS・GPUへの実際の表示時刻や指のタップ遅延ではありません。3標本で、初期表示付近・倍率100%の結果です。長時間利用後、全件閲覧後、ズーム中、競合・保存失敗時、同一スペースの複数品目、スマートフォン実機で同じ改善が得られるとは断定できません。実行モードの確認画面と回答記録の反応には追加の原因調査と改善が必要です。

`compare.mjs` が実行した測定スクリプト、`raw.jsonl` が本測定の全ログ、`summary.json` が最小・最大・中央値と個別値です。準備中の失敗したパイロット測定は本測定に含めていません。スクリプトのPlaywright importは本ワークスペースへの絶対パスです。変更前・変更後のVite previewをそれぞれ4271・4272番ポートで起動してから `node compare.mjs` を実行します。
